# Лабораторная работа №2

## Описание задания

RAG-агент по корпусу научных статей: спарсить источники в нормализованный Markdown с метаданными, разбить на чанки и построить dense- и sparse-эмбеддинги с конфигурируемой стратегией, загрузить индекс в векторное хранилище, собрать набор оценочных вопросов с эталонными источниками, измерить Recall@k/Precision@k/MRR на нескольких конфигурациях чанкинга и векторизации и реализовать движок ответа: поиск релевантных чанков → сборка промпта → вызов LLM → ответ с цитатами.

Архитектура сервиса (FastAPI + Qdrant + сервисный слой) построена по образцу учебного проекта `book-rag` — того же паттерна «тонкие роуты → сервисы», что и в лабораторной работе 1, только без привязки к одной книге (`book_id`): поиск и загрузка ведутся по всему корпусу сразу.

## Использованные технологии и модели

Оборудование и ОС — те же, что в лабе 1 (NVIDIA GeForce RTX 3070 Laptop, 8 ГБ видеопамяти, WSL2 Ubuntu).

Корпус: 23 статьи с arXiv по теме «retrieval augmented generation» (архитектуры RAG, оценка RAG-пайплайнов, графовый/hypergraph RAG, чанкинг, multi-hop retrieval), 412 страниц, ~1.39 млн знаков. Скачаны `scripts/download_corpus.py` (поиск по arXiv API, пауза между запросами); тема выбрана осознанно — она прямо совпадает с механикой самой лабы, поэтому содержание статей понятно без специальной подготовки.

LLM: Qwen/Qwen2.5-7B-Instruct-AWQ через vLLM — тот же сервер, что в лабе 1 (`http://localhost:8000`).

Фреймворки и библиотеки:
- FastAPI — API-сервис (`book_rag_backend/app.py`);
- Qdrant (Docker, `qdrant/qdrant`) — векторное хранилище;
- fastembed — и dense-, и sparse-эмбеддинги, единая библиотека для обоих типов: dense-модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (`TextEmbedding`), sparse — `Qdrant/bm25` (`SparseTextEmbedding`);
- langchain-text-splitters (`RecursiveCharacterTextSplitter`) — сплиттер;
- pdfplumber, pandas, tabulate — парсинг PDF и таблиц;
- httpx — клиент к LLM (OpenAI-совместимый REST, без SDK).

## Результаты работы

### Парсинг в Markdown (п. 2)

`ParserService` (`book_rag_backend/services/parser.py`) разбирает PDF постранично: определяет двухколоночную вёрстку по координатам слов и восстанавливает порядок чтения (сначала левая колонка целиком, потом правая), выносит таблицы в Markdown-таблицы отдельно от текста (с фильтром ложных «таблиц» — рисунков с рамками, которые `pdfplumber` иногда принимает за таблицы), определяет заголовки разделов по сочетанию нумерации (`3.1`, `4.2` и т. п.) и размера шрифта, убирает повтор названия статьи, которым часто начинается сам текст PDF. Поддерживается только PDF — весь корпус в этом формате, остальные форматы из задания (DOCX/PPTX/HTML/MD) не нужны «в зависимости от корпуса».

Результат — один `.md`-файл на документ в `data/markdown/`, с YAML-шапкой (`source`, `date`, число страниц) и маркерами `<!-- page: N -->` по тексту.

Итог по корпусу: 23 документа, 412 страниц, 1 392 138 знаков после нормализации (2 статьи из скачанных 25 оказались повреждены при скачивании/упаковке и исключены).

### Чанкинг и эмбеддинги (п. 3)

`SplitterService` — `RecursiveCharacterTextSplitter` (рекурсивный, по разделителям от абзацев до отдельных слов), `chunk_size` считается в словах как приближение токена. Отдельно, для каждого чанка определяется **ближайший заголовок раздела** на той же странице (без переноса между страницами — умышленно простой вариант, без отдельного состояния между страницами) — он кладётся в метаданные (`heading`) и, если включён `include_headings`, приклеивается к тексту перед эмбеддингом.

Эмбеддинги — `EmbeddingsService` (dense, `fastembed.TextEmbedding`, модель `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, 384-мерный вектор) и `SparseEmbeddingsService` (sparse, `fastembed.SparseTextEmbedding("Qdrant/bm25")` — готовая реализация классического BM25 из самого `fastembed`, а не собственная формула; TF и IDF считает библиотека). Поддерживаются режимы `dense`, `sparse`, `hybrid`.

Все параметры конфигурируются тремя способами:
- **`config.yml`** — базовые значения по умолчанию (`splitter.chunk_size`, `splitter.chunk_overlap`, `splitter.include_headings`, `embeddings.vectorizer`, `embeddings.dense_model`, HNSW-параметры и т. д.);
- **`.env`** — секреты и адреса (`QDRANT_URL`, `QDRANT_API_KEY`, `LLM_URL`, `LLM_API_KEY`), перетирают `config.yml`;
- **флаги командной строки** — перетирают всё: `--chunk-size`, `--overlap`, `--include-headings`, `--vectorizer`, `--dense-model`, `--hnsw-m`, `--ef-construct`, `--ef-search`.

Артефакты (`artifacts/chunks.jsonl`, `dense.npy`, `sparse.jsonl`, `manifest.json`) версионируются через `manifest.json`: при каждом запуске `scripts/build_index.py` сверяет записанные там параметры сборки с текущими — если совпадают, пересчёт пропускается («индекс уже собран»); если нет (или передан `--force`) — пересобирается заново, причём старые `dense.npy`/`sparse.jsonl` сначала удаляются, чтобы при смене `vectorizer` не остался файл от предыдущей конфигурации с другим числом векторов.

### Векторное хранилище (п. 4)

Qdrant (Docker, локально), коллекция `rag_chunks` с именованными векторами `dense` (384-мерный, COSINE) и/или `sparse`, в зависимости от `vectorizer`. HNSW-параметры (`hnsw_m`, `hnsw_ef_construct` — при создании коллекции; `hnsw_ef_search` — при поиске) берутся из `config.yml`.

Id точки в Qdrant — детерминированный UUID, полученный из хэша чанка (`uuid5`) — Qdrant принимает только целые числа или UUID, поэтому короткий hex-хэш чанка конвертируется в UUID; один и тот же чанк всегда даёт один и тот же id, повторная загрузка не создаёт дублей.

`scripts/load_to_vector_store.py` идемпотентен: если коллекция уже существует и число точек совпадает с числом чанков — ничего не делает; `--rebuild` удаляет и грузит заново; `--reset` — просто сбрасывает коллекцию. Отдельная проверка защищает от рассинхрона: если число векторов в `dense.npy`/`sparse.jsonl` вдруг не совпадёт с числом строк в `chunks.jsonl` — скрипт остановится с понятной ошибкой, а не упадёт где-то в середине загрузки.

### Оценочные вопросы и метрики (п. 1, п. 5)

16 вопросов на английском языке (том же, что и корпус) — намеренно **общие, про устройство RAG как такового** (зачем нужен retrieval, dense/sparse/hybrid, chunking, multi-hop retrieval и т. п.), а не вопросы по узким деталям конкретной статьи. Каждый привязан к конкретной статье/странице, где эта мысль сформулирована, эталон `{source, page}` в `eval/questions.jsonl`.

Сравнение трёх конфигураций (`scripts/run_experiments.py`, `experiments.yml`), k = 5 и 10 — каждая цельная конфигурация сплиттера + эмбеддингов, а не точечное изменение одного параметра:

| Конфигурация | chunk_size | overlap | заголовки | vectorizer | Чанков | Recall@5 | Precision@5 | Recall@10 | Precision@10 | MRR |
|---|---|---|---|---|---|---|---|---|---|---|
| fast-sparse | 200 | 30 | нет | sparse | 1604 | 0.938 | 0.275 | **1.0** | **0.15** | **0.859** |
| balanced-hybrid | 300 | 50 | да | hybrid | 1079 | 0.812 | 0.225 | **1.0** | **0.15** | 0.534 |
| thorough-dense | 500 | 100 | да | dense | 682 | 0.188 | 0.05 | 0.25 | 0.031 | 0.075 |

Коротко: `thorough-dense` (только dense) почти не справляется с этим корпусом — Recall@10 всего 0.25, 12 из 16 вопросов вообще не находятся в топ-10. `sparse` и `hybrid` оба выходят на Recall@10 = 1.0, но по MRR `sparse` заметно обгоняет `hybrid` (0.859 против 0.534). Подробный разбор — в «Выводах» ниже.

Для каждой конфигурации сохранён не только агрегат, но и сырые найденные чанки на каждый вопрос (`results/retrieval_dump_<имя>.json`) — чтобы можно было свериться глазами, что реально нашлось, а не доверять только итоговым числам.

### Движок ответа (п. 6)

`RAGService.search()`: эмбеддинг вопроса (dense и/или sparse) → поиск в Qdrant (для `hybrid` — RRF-слияние dense- и sparse-результатов) → сборка промпта (системная инструкция + история диалога + пронумерованный контекст из найденных чанков, с ограничением по общему числу символов) → вызов LLM (Qwen2.5-7B-Instruct-AWQ) → ответ с цитатами (источник, страница, заголовок раздела, score, сниппет). Эндпоинт — `POST /search`.

Пример работы (вопрос из `eval/questions.jsonl`):

Вопрос: *«What does the Ragas framework evaluate about a RAG pipeline without relying on human-annotated ground truth answers?»*

Источник — `papers/2309.15217.pdf`, стр. 1: *«We introduce Ragas (Retrieval Augmented Generation Assessment), a framework for reference-free evaluation of Retrieval Augmented Generation (RAG) pipelines... we put forward a suite of metrics which can be used to evaluate these different dimensions without having to rely on ground truth human annotations.»* Живой ответ модели с цитатами (`POST /search`) проверяется через Postman-коллекцию (`lab2-rag.postman_collection.json`) на поднятом сервисе.

Пайплайн целиком (health check → `/search` → `/documents` list) проверяется вживую через Postman-коллекцию (`lab2-rag.postman_collection.json`) на поднятом сервисе.

Дополнительно реализован `POST /documents` — загрузка одного PDF в уже работающую коллекцию через API (не требование задания, добавлено отдельно): принимает `chunk_size`/`chunk_overlap`/`include_headings` прямо в запросе, переопределяя конфиг сервера для этой конкретной загрузки.

## Выводы

**Только dense почти не работает на этом корпусе.** `thorough-dense` (крупные чанки, 500 токенов, только смысловой поиск) — Recall@10 всего 0.25: из 16 вопросов находит релевантный чанк лишь для четырёх. Корпус — статьи про сам RAG, где одни и те же термины (retrieval, chunking, hybrid search, dense/sparse) используются почти во всех документах практически одинаково; смысловая близость здесь работает заметно хуже точного лексического совпадения, потому что модели трудно отличить одну статью про RAG от другой по общему смыслу.

**BM25 (sparse) заметно сильнее dense в одиночку** и по Recall (1.0 против 0.25), и по MRR (0.859 против 0.075) — вопросы используют почти те же формулировки, что и текст источников, а в этом лексический поиск точнее смыслового.

**Неожиданный результат: `hybrid` проигрывает чистому `sparse` по MRR** (0.534 против 0.859), хотя Recall у обоих 1.0. По вопросам видно механику: там, где `sparse` ставит верный чанк на 1-е место, `hybrid` часто сдвигает его на 2-3-е (например, вопросы 4, 5, 6, 7, 10, 13, 16 — у sparse ранг 1, у hybrid 2-3). Причина — RRF-слияние комбинирует ранги из обоих списков поровну; раз dense на этом корпусе работает плохо сам по себе (часто вообще не находит нужный чанк в своём топе), он «утягивает» итоговый ранг вниз даже там, где sparse уже нашёл точный ответ на первом месте. Вывод: гибридный поиск не гарантированно лучше лучшего из двух базовых методов — если один компонент заметно слабее другого на конкретном корпусе, наивное RRF-слияние может только испортить результат сильного метода.

**Про формулировку вопросов.** Изначально три вопроса («какую проблему решает RAG», «из каких частей состоит пайплайн») были сформулированы максимально обще и не находились ни в одной конфигурации — не из-за отказа поиска, а потому что в корпусе из статей на одну тему несколько документов формулируют один и тот же тезис похожими словами, и у вопроса физически не было единственного правильного источника. После переформулировки на конкретный, отличительный вклад каждой статьи (не «что такое RAG», а «какую именно атаку выполняет Interrogation Attack», «какие два фреймворка интегрирует Ragas» и т. п.) все вопросы нашлись корректно. Урок: вопрос может быть общим по теме, но должен быть заземлён на то, что сформулировано уникальным образом именно в одном источнике, а не на тезис, который мог бы повторить любой документ корпуса.

Для продакшен-конфигурации на этом корпусе: `sparse`-only — не просто дешевле (не нужно считать dense-эмбеддинги вообще), но и заметно надёжнее по MRR, чем `hybrid`. Показательный пример того, что оптимальная конфигурация зависит от конкретного корпуса и её нужно подбирать эмпирически, а не фиксировать раз и навсегда.

## Инструкция по запуску

Нужны: Windows с WSL2 (Ubuntu), NVIDIA-видеокарта с драйвером, поддерживающим CUDA 13 (в WSL ставить не нужно), Docker.

1. Окружение (отдельное от vLLM из лабы 1):
```bash
python3 -m venv ~/venv-rag
source ~/venv-rag/bin/activate
pip install -r source/requirements.txt
```

2. Поднять Qdrant:
```bash
docker run -d --name qdrant -p 6333:6333 -p 6334:6334 qdrant/qdrant
# при повторных запусках, если контейнер уже создан: docker start qdrant
```

3. Скачать корпус (один раз; если уже скачан — пропустить):
```bash
cd source
python scripts/download_corpus.py --arxiv-query "retrieval augmented generation" --max 25
```

4. Поднять vLLM с моделью из лабы 1 (отдельное окно, свой venv):
```bash
source ~/venv-vllm/bin/activate
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --max-model-len 4096 --gpu-memory-utilization 0.86 \
    --max-num-seqs 16 --max-num-batched-tokens 1024 --generation-config vllm \
    --no-enable-prefix-caching --port 8000
```

5. Собрать индекс и загрузить в Qdrant:
```bash
python scripts/build_index.py
python scripts/load_to_vector_store.py
```

6. Прогнать поиск и сохранить результаты (ручная проверка перед метриками):
```bash
python scripts/evaluate.py
```

7. Сравнить конфигурации (несколько полных пересборок подряд, долго):
```bash
python scripts/run_experiments.py
```
Результат — `results/retrieval_dump_<имя>.json` на каждую конфигурацию из `experiments.yml`; метрики по ним считаются отдельно.

8. **Важно:** `run_experiments.py` оставляет коллекцию `rag_chunks` в состоянии **последней** конфигурации из `experiments.yml` (`thorough-dense` — только dense, без sparse), а не твоего рабочего `config.yml` (`balanced-hybrid`). Перед запуском сервиса нужно пересобрать и перезагрузить индекс ещё раз под боевой конфиг, иначе `/search` упадёт (сервис прочитает `vectorizer: hybrid` из конфига, а в реальной коллекции sparse-векторов не окажется):
```bash
python scripts/build_index.py --force
python scripts/load_to_vector_store.py --rebuild
```

9. Запустить сервис и обратиться к `/search` (из папки `source/` — там лежит пакет `book_rag_backend`):
```bash
cd source   # если терминал ещё не в этой папке
python -m book_rag_backend.app
```
```bash
curl -s -X POST http://localhost:8001/search \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"<вопрос>"}]}'
```
