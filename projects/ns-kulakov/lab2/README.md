# Лабораторная работа №2

## Построение RAG-агента по документации

## Описание задания

Цель лабораторной работы — разработать RAG-систему, которая использует корпус документов для поиска релевантной информации и формирования ответов языковой модели с указанием источников.

В рамках работы выполнены следующие задачи:

1. Подготовлен корпус документов объёмом более 50 страниц.
2. Реализовано извлечение текста из PDF и преобразование в Markdown с метаданными.
3. Реализованы разбиение документов на чанки и построение эмбеддингов.
4. Развёрнуто векторное хранилище Qdrant и загружен индекс.
5. Реализованы Dense, Sparse и Hybrid Retrieval.
6. Проведена оценка качества поиска по метрикам Recall@k, Precision@k и MRR.
7. Реализован RAG-пайплайн с использованием LLM и цитированием источников.

## Реализация парсинга и чанкинга

PDF обрабатывается с помощью PyMuPDF. Для каждой страницы извлекается текст, после чего он сохраняется в Markdown. Вместе с текстом сохраняются метаданные:

- идентификатор документа;
- имя исходного файла;
- URL источника;
- физический номер страницы PDF;
- идентификатор и название раздела.

Для разбиения документов реализованы две стратегии:

1. **Recursive Chunking** — разбиение текста по естественным границам абзацев и предложений.
2. **Markdown-aware Chunking** — разбиение с учётом заголовков и структуры Markdown.

Размер чанка и overlap задаются в токенах с использованием токенизатора BGE-M3. При включённой настройке в текст чанка добавляются название раздела и номер страницы.

Каждый чанк содержит `chunk_id`, `document_id`, `section_id`, `section_title`, `pdf_page`, текст и количество токенов.

Для каждой конфигурации создаётся отдельный индекс. В `manifest.json` сохраняются хеш исходного PDF, параметры чанкинга, embedding-модель, диапазон страниц, количество чанков и размерность матрицы эмбеддингов.

## Построение эмбеддингов и векторное хранилище

Для построения dense-векторов используется `BAAI/bge-m3` через SentenceTransformers. Модель поддерживает мультиязычные тексты, что позволяет обрабатывать русскоязычные запросы к англоязычному учебнику.

Полученные эмбеддинги нормализуются и сохраняются в `vectors.npy`. Размерность каждого вектора — 1024.

Для хранения используется Qdrant. В коллекцию загружаются векторы и соответствующие метаданные чанков. Для поиска применяется cosine similarity и HNSW со следующими параметрами:

- `M = 16`;
- `ef_construct = 100`;
- `ef_search = 64`.

Повторная загрузка выполняется через `upsert`, а идентификаторы точек формируются на основе стабильных ID чанков.

## Реализация Retrieval

В проекте доступны три режима поиска.

### Dense Retrieval

Вопрос преобразуется в embedding с помощью BGE-M3. Qdrant возвращает наиболее близкие векторы и соответствующие им текстовые чанки.

### Sparse Retrieval

Для лексического поиска используется BM25 из библиотеки `rank-bm25`. Метод учитывает совпадения терминов запроса с текстом документов.

### Hybrid Retrieval

Результаты Dense и Sparse Retrieval объединяются с помощью Reciprocal Rank Fusion. RRF использует позиции документов в двух ранжированных списках и формирует общий рейтинг.

Для работы с русскоязычными вопросами к англоязычному корпусу в поиске предусмотрено расширение статистических терминов английскими эквивалентами.

## Эксперименты

Для сравнения чанкинга и retrieval подготовлены три конфигурации.

| Параметр | E1 | E2 | E3 |
|---|---|---|---|
| Стратегия чанкинга | Recursive | Markdown | Markdown |
| Размер чанка | 300 | 600 | 600 |
| Overlap | 50 | 100 | 100 |
| Retrieval | Dense | Dense | Hybrid |
| Embedding-модель | BGE-M3 | BGE-M3 | BGE-M3 |
| Количество чанков | 449 | 226 | 226 |

В E1 используется рекурсивное разбиение с размером чанка 300 токенов и overlap 50. В E2 применяется разбиение с учётом структуры Markdown, размер чанка составляет 600 токенов, overlap — 100. В E3 используются параметры чанкинга E2 и гибридный поиск Dense + BM25.

### Метрики оценки

- **Recall@k** — доля эталонных релевантных разделов, найденных среди первых `k` результатов.
- **Precision@k** — доля релевантных разделов среди первых `k` результатов.
- **MRR@k** — обратный ранг первого найденного релевантного раздела.
- **Latency** — среднее время поиска в миллисекундах.

Метрики рассчитываются на уровне уникальных разделов: несколько найденных чанков одного раздела учитываются как один результат. Перед измерением времени выполняется прогрев embedding-модели.

## Результаты работы

### Сравнение на всей выборке (18 вопросов)

| Конфигурация | Recall@5 | Precision@5 | MRR@5 | Recall@10 | Precision@10 | MRR@10 | Latency, мс |
|---|---:|---:|---:|---:|---:|---:|---:|
| E1 — Recursive + Dense | **1.0000** | **0.2111** | **0.9278** | **1.0000** | **0.1056** | **0.9278** | **138.82** |
| E2 — Markdown + Dense | 1.0000 | 0.2111 | 0.8704 | 1.0000 | 0.1056 | 0.8704 | 141.38 |
| E3 — Markdown + Hybrid | 0.9444 | 0.2000 | 0.7963 | 0.9444 | 0.1000 | 0.7963 | 140.02 |

### Результаты на отложенной выборке Test (6 вопросов)

| Конфигурация | Recall@5 | Precision@5 | MRR@5 | Latency, мс |
|---|---:|---:|---:|---:|
| E1 — Recursive + Dense | 1.0000 | 0.2000 | 0.8667 | 142.01 |
| E2 — Markdown + Dense | 1.0000 | 0.2000 | **0.8889** | 145.48 |
| E3 — Markdown + Hybrid | 1.0000 | 0.2000 | 0.7222 | 140.36 |

### Анализ результатов

- E1 и E2 нашли все эталонные разделы на всей выборке: Recall@5 и Recall@10 составили 1.0.
- E1 показала наибольший MRR на всей выборке — 0.9278. Релевантные разделы в среднем располагаются выше в выдаче, чем в других конфигурациях.
- E2 показала Recall@5 = 1.0 и MRR@5 = 0.8704 на всей выборке. На отложенной выборке E2 получила наибольший MRR@5 — 0.8889.
- E3 показала Recall@5 = 0.9444 и MRR@5 = 0.7963 на всей выборке. На test-части Recall@5 составил 1.0.
- Среднее время retrieval для трёх конфигураций находится в диапазоне 138.82–141.38 мс.
- E1 формирует 449 чанков, а E2 и E3 — по 226 чанков. При этом E1 показала наилучшее ранжирование релевантных разделов на полной выборке.

Precision@5 рассчитывается по пяти уникальным найденным разделам. Поэтому значение 0.2 означает, что среди первых пяти разделов один является релевантным. При этом Recall@5 может быть равен 1.0, если все эталонные разделы вопроса найдены.

## Реализация RAG-пайплайна

Полный RAG-пайплайн реализован в `scripts/pipeline.py`.

Последовательность обработки запроса:

1. Вопрос пользователя передаётся в Retriever.
2. Выполняется поиск релевантных чанков в выбранном режиме: Dense, Sparse или Hybrid.
3. Из найденных чанков формируется контекст с ограничением `max_context_tokens = 2000`. В контекст включается не более двух чанков с одной физической страницы.
4. Каждому источнику присваивается идентификатор `[S1]`, `[S2]` и т. д.
5. Вопрос и контекст передаются Qwen3 4B через OpenAI-совместимый API Ollama.
6. Модель формирует ответ на русском языке с указанием идентификаторов источников.
7. Программа сопоставляет использованные ID с переданными источниками и возвращает сведения о документах, разделах, страницах PDF, текстовых фрагментах и retrieval score.

Параметры генерации:

- `temperature = 0.2`;
- `max_tokens = 650`.

Системный промпт хранится отдельно в `prompts/rag_system.md`.

### REST API

Для взаимодействия с RAG реализован API на FastAPI.

| Метод и endpoint | Назначение |
|---|---|
| `GET /health` | Проверка доступности сервиса |
| `GET /index/info` | Информация об активном пресете, индексе и коллекции |
| `POST /search` | Поиск релевантных фрагментов без генерации |
| `POST /ask` | Полный RAG-запрос с генерацией ответа |

## Инструкция по запуску

### 1. Установка зависимостей

Из корневой папки проекта:

```powershell
python -m venv venv
.\venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Запуск Qdrant

Запустить Qdrant в Docker:

```powershell
docker run -d --name reprolab-qdrant -p 6333:6333 -v reprolab_qdrant:/qdrant/storage qdrant/qdrant:v1.15.4
```

Адрес Qdrant: `http://127.0.0.1:6333`.

### 3. Запуск Ollama

Установить Ollama и загрузить модель:

```powershell
ollama pull qwen3:4b-instruct-2507-q4_K_M
ollama serve
```

### 4. Парсинг, построение и загрузка индекса

```powershell
python scripts/main.py parse
python scripts/main.py build --preset e1 --rebuild
python scripts/main.py load --preset e1 --reset
```

### 5. Оценка и сравнение retrieval

Оценка выбранной конфигурации:

```powershell
python scripts/main.py evaluate --preset e1 --split all
```

Сравнение конфигураций E1, E2 и E3:

```powershell
python scripts/main.py compare
```

Результаты сохраняются в каталоге `results/`.

### 6. Проверка поиска и RAG

Поиск без генерации:

```powershell
python scripts/main.py search "Что такое p-value?" --preset e1
```

Полный RAG-запрос:

```powershell
python scripts/main.py ask "Что такое p-value?" --preset e1
```

### 7. Запуск REST API

```powershell
python scripts/main.py serve
```

После запуска документация API доступна по адресу:

`http://127.0.0.1:8000/docs`
