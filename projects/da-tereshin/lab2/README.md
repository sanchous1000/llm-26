# Лабораторная работа №2 (Построение RAG-агента по документации)

## Описание задания

1. Выбрать и подготовить источники данных
2. Спарсить источники в Markdown
3. Разбить на чанки и построить эмбеддинги (sparse/dense)
4. Развернуть векторное хранилище и загрузить индекс
5. Выбрать метрики и оценить качества retrieval/QA
6. Реализовать движок общения (RAG-пайплайн)

## Использованные технологии и модели

**Модели:**

* `qwen3.5:4b` — генерация ответов, reasoning отключён (`think=false`).
* `BAAI/bge-m3` — dense-эмбеддинги документов и вопросов.
* `Qwen/Qwen3.5-4B` — токенизатор для расчёта бюджета контекста LLM.

**Фреймворки и инструменты:**

* Ollama — локальный запуск LLM через REST API.
* Sentence Transformers и PyTorch — вычисление эмбеддингов.
* FAISS — векторный поиск с индексами Flat, HNSW и HNSW-PQ.
* Streamlit — интерфейс для вопросов и просмотра источников ответа.
* Tesseract OCR с языковыми данными `rus` и `eng` — распознавание сканированных страниц PDF; устанавливается отдельно от Python-пакетов.

**Библиотеки:**

* `PyMuPDF`, `pymupdf4llm` — чтение PDF и преобразование в Markdown.
* `langchain-text-splitters`, `tiktoken` — разбиение текста и подсчёт токенов чанков.
* `transformers`, `huggingface-hub` — загрузка токенизаторов и определение ревизии модели эмбеддингов.
* `numpy` — обработка векторов и расчёт метрик.
* `requests` — HTTP-запросы к Ollama.
* `PyYAML` — чтение конфигурации и метаданных страниц.

### Этап 1. Выбрать и подготовить источники данных

В качестве корпуса документов были взяты дополнительные материалы к курсу "Визуальные формы мышления". Всего в базе 5 документов:

1. Малви Л. «Визуальное удовольствие и нарративный кинематограф» — 18 стр.
2. Нерони Х. «Наслаждение по Джейн Кэмпион» — 16 стр.
3. Кэрролл Н. «Notes on the Sight Gag» (из «Theorizing the Moving Image») — 12 стр.
4. Вертов Д. «Мы. Вариант манифеста» — 8 стр.
5. Барт Р. «Риторика образа» — 22 стр.

Суммарно: 76 страниц

Исходные PDF доступны в [папке на Google Диске](https://drive.google.com/drive/folders/1vVP41k8wjf9RCyovEUi4wqX7BSWMIY3r).
Перед запуском обработки скачать их в `data/raw/` внутри `lab2`, сохранив имена
файлов, указанные в `conversion.documents` в `config.yaml`.

По этим документам были подготовлены 15 репрезентативных вопросов с эталонными ответами и ссылками. Они размещены в файле `questions.md` с единой структурой.

### Этап 2. Спарсить источники в Markdown

Для перевода PDF в Markdown использую PyMuPDF4LLM и PyMuPDF (+ Tesseract OCR). Каждая страница сохраняется в отдельный .md-файл с метаданными: источник, номер страницы и способ извлечения.

Далее на этапе проверки результатов конвертации было принято решение сделать в конфиге выбор для каждого документа, подключать OCR или нет. Это сделано, потому что у исходных PDF разное качество текстового слоя. Один способ извлечения для всех документов давал неудовлетворительный результат.

| Документ | Что обнаружилось | Выбранный режим |
|---|---|---|
| **Вертов — «Мы. Вариант манифеста»** | Без OCR основной текст отсутствовал: извлекались преимущественно служебные строки, URL и номера страниц. С OCR появился содержательный текст, но на странице 6 остался большой фрагмент шума | С OCR |
| **Малви — «Визуальное удовольствие и нарративный кинематограф»** | Без OCR встречались сильно испорченные последовательности символов. После OCR основной текст стал читаемым | С OCR |
| **Барт — «Риторика образа»** | Без OCR текст извлекался, но встречались разрывы слов | Без OCR |
| **Кэрролл — «Notes on the Sight Gag»** | Без OCR текст извлекался; были подозрения на перемешивание колонок, требующие сверки с PDF | Без OCR |
| **Нерони — «Наслаждение по Джейн Кэмпион»** | В предыдущей проверке существенных проблем извлечения не отмечено | Без OCR |

То есть для последних трех документов результат с OCR давал примерно такой же результат.

После конвертации PDF в Markdown добавлен отдельный этап минимальной нормализации: удаление мягких переносов, замена неразрывных пробелов обычными и очистка концов строк с сохранением структуры Markdown. Чтобы не «переобучать» подготовку данных под выбранную базу документов, правила для отдельных авторов, страниц и ошибок распознавания не добавлялись. Такой подход применим к новым документам, однако не устраняет OCR-шум, нарушения порядка чтения колонок и другие ошибки извлечения текста.

### Этап 3. Разбить на чанки и построить эмбеддинги (sparse/dense)

Для разбиения Markdown-документов на чанки реализовано два сплиттера из langchain-text-splitters (`MarkdownHeaderTextSplitter` и `RecursiveCharacterTextSplitter`), объединённые в гибридную схему.

Для построения dense-эмбеддингов использовалась BGE-M3 (https://huggingface.co/BAAI/bge-m3), размерность 1024, формат float32. 

Все параметры регулируются через config.yaml.

Размер чанков задаётся в токенах `cl100k_base`. В `split.py` каждый сформированный
чанк дополнительно проверяется токенизатором модели эмбеддингов, включая
специальные токены: его длина не должна превышать `model_max_length`.

В `embed.py` перед вычислением эмбеддингов длины всех чанков повторно проверяются
по токенизатору загруженной модели и её `max_seq_length`. При превышении лимита
выбрасывается ошибка вместо молчаливого обрезания текста. Эти проверки относятся
к входу модели эмбеддингов; бюджет контекста генеративной LLM проверяется отдельно
на этапе формирования запроса.

### Этап 4. Развернуть векторное хранилище и загрузить индекс

Для построения индекса использовалась библиотека FAISS.
В скрипте реализована возможность строить три индекса:

* Flat
* HNSW
* HNSW-PQ

Для дальнейших экспериментов был выбран HNSW без квантизации.
Корпус содержит лишь несколько сотен векторов: этого мало для качественного обучения PQ, а экономия памяти при таком объёме несущественна. Параметры HNSW во всех экспериментах зафиксированы, чтобы сравнивать влияние разбиения на чанки.

Параметры HNSW: `M=16`, `ef_construction=100`, `ef_search=32`.
Эмбеддинги документов и запросов нормализуются до единичной длины.
Поиск использует квадрат евклидова расстояния (Squared L2): меньшее значение
означает более близкий вектор; для нормализованных векторов порядок совпадает
с ранжированием по косинусному сходству.

Каждый запуск чанкинга и построения эмбеддингов создаёт отдельную папку
с временной меткой и `manifest.json`. Метаданные сохраняют параметры,
ревизию модели и контрольные суммы для проверки согласованности артефактов.
Индекс хранится в фиксированной папке `vector_store.output_dir`.
Повторная загрузка тех же данных и параметров оставляет существующий индекс;
при их изменении скрипт требует `--rebuild`. Этот флаг удаляет старый индекс
и строит новый, а `--drop-index` только удаляет его файлы.

### Этап 5. Метрики и оценка качества retrieval/QA

Был собран `questions.json` на основе базы вопросов для удобного расчета метрик.

Далее было проведено три эксперимента с полной пересборкой чанков, эмбеддингов и индекса на единой базе документов. Результаты сравнивались по набору метрик из задания. Дополнительно сравнивались top-5 и top-10.

`evaluate.py` рассчитывает Hit@k, MRR@k и Recall@k для текущего индекса.
Полную сравнительную таблицу воспроизводит `source/tests/run_experiments.py`:
он дополнительно рассчитывает Precision@k и объём найденного контекста.
Precision@k — доля позиций top-k, принадлежащих эталонным страницам.

Метрики усредняются по вопросам. Повторные чанки одной
страницы не увеличивают Recall, но учитываются в Precision.

| hybrid | 400 / 60 | 380 | 10 | 0,9333 | 0,6056 | 0,9000 | 0,2133 | 3285 |
| hybrid | 700 / 100 | 235 | 5 | 0,8667 | 0,5744 | 0,8000 | 0,2933 | 2654 |

### Этап 6. Генерация ответа и подбор контекста

RAG-пайплайн реализован в `source/service/rag.py`: вопрос кодируется моделью
эмбеддингов, FAISS возвращает ближайшие чанки, затем из них формируется запрос
к Ollama. Системная инструкция требует отвечать по предоставленным фрагментам,
указывать их номера в квадратных скобках и сообщать о недостатке сведений.

Чтобы не выйти за окно контекста, метод `pack_context()` рассчитывает бюджет входа:
`num_ctx - num_predict - token_margin`. При текущих настройках это
`16384 - 768 - 128 = 15488` токенов: место для ответа и запас зарезервированы заранее.

Сначала подсчитываются токены инструкции и вопроса без фрагментов. Если уже они
превышают бюджет, выбрасывается `ValueError` с предложением сократить вопрос.
Затем чанки добавляются по одному в порядке результатов поиска. Для каждого
кандидата заново подсчитывается весь запрос с помощью токенизатора
`Qwen/Qwen3.5-4B` и его chat template, включая оформление сообщений и фрагментов.
Если очередной чанк не помещается, добавление прекращается: этот и последующие
чанки не отправляются, а ранее выбранные сохраняются целиком.

Пример фактического ответа с источниками, метриками и разбором ошибок приведён
в [rag_example.md](rag_example.md).

### Интерфейс Streamlit

В `source/service/app.py` реализован интерфейс: можно выбрать готовый вопрос
или ввести свой. Он показывает ответ, время поиска и генерации, оценку токенов
до отправки, фактическое число входных токенов и использованный бюджет контекста.
Для отправленных фрагментов доступны текст, документ, PDF-страница и расстояние
Squared L2; для готовых вопросов также можно раскрыть эталонный ответ и цитаты.
Если часть чанков не поместилась в контекст или ответ достиг лимита генерации,
интерфейс выводит предупреждение. Ошибка превышения бюджета вопросом также
отображается пользователю.

## Выводы

Ошибки в работе пайплайна могут возникать на каждом из его этапов (если реализована плохая конвертация, не проведена достаточная чистка, выбран неподходящий тип чанкинга и т.д.).

### Выводы по экспериментам

- При переходе hybrid 400/60 → 700/100 меняются одновременно размер и overlap.
  Recall@5 растёт с 0,7667 до 0,8000, но средний контекст увеличивается
  примерно на 54%. MRR@5 немного снижается.
- При одинаковых 700/100 recursive даёт ту же полноту, что и hybrid, и лучший
  MRR: 0,6078 против 0,5744 при k=5. Обработка заголовков hybrid на этом
  корпусе не дала преимущества по выбранным метрикам.
- Для следующего этапа выбран **recursive 700/100** как вариант с лучшим MRR
  и максимальной измеренной полнотой при k=10. Этот вариант установлен в рабочем конфиге.
  При ограниченном бюджете контекста стоит рассматривать hybrid 400/60:
  его top-10 занимает около 3285 токенов при Recall=0,9000.
- У recursive переход k=5 → 10 повышает Recall с 0,8000 до 0,9667,
  увеличивая контекст с 2688 до 4988 токенов.

Разбор конкретных вопросов

- q08: эталонная страница появляется на ранге 6 у hybrid 400/60, 8 у
  hybrid 700/100 и 7 у recursive 700/100; top-5 её не содержит.
- q10: уменьшение чанков поднимает эталонную страницу Кэрролла с ранга 9
  на ранг 3. Это не подтверждает исправление порядка колонок в исходном тексте.
- q11: у hybrid 400/60 эталонной страницы нет даже в top-10;
  у обоих вариантов 700/100 она на третьем месте.
- q12: hybrid 400/60 находит обе эталонные страницы уже в top-5;
  варианты 700/100 находят вторую страницу только на ранге 10.
- q15: во всех вариантах top-10 содержит страницу Нерони, но не содержит
  эталонную страницу 16 Малви; Recall вопроса остаётся 0,5.

## Инструкция по запуску

Все команды ниже выполняются из папки лабораторной:

```bash
cd projects/da-tereshin/lab2
python -m pip install -r source/requirements.txt
```

Перед выполнением этапов с эмбеддингами и запуском интерфейса ограничить
число потоков нативных библиотек в этом же терминале. В использованном окружении
это позволило избежать `Segmentation fault` при запуске RAG:

```bash
export OMP_NUM_THREADS=1
export MKL_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
export TOKENIZERS_PARALLELISM=false
```

Для OCR требуется Tesseract с языковыми данными `rus` и `eng`.
Скрипт `convert.py` ищет их в `share/tessdata` внутри используемого
Python-окружения (`sys.prefix`). Установить Ollama и скачать модель:

```bash
ollama pull qwen3.5:4b
```

Если сервер Ollama не запущен через приложение, запустить в отдельном терминале
`ollama serve` и оставить работающим.

### Подготовка корпуса и индекса

1. Скачать PDF из [папки на Google Диске](https://drive.google.com/drive/folders/1vVP41k8wjf9RCyovEUi4wqX7BSWMIY3r)
   в `data/raw/`, сохранив имена файлов из `config.yaml`.
2. Преобразовать документы и нормализовать Markdown:

   ```bash
   python source/scripts/convert.py
   python source/scripts/md_cleaning.py
   ```

3. Построить чанки:

   ```bash
   python source/scripts/split.py
   ```

   Вручную записать путь к созданной папке из вывода скрипта в
   `embedding.chunks_dir` в `config.yaml`.

4. Вычислить эмбеддинги:

   ```bash
   python source/scripts/embed.py
   ```

   Вручную записать путь к созданной папке в `vector_store.embeddings_dir`.
   При первом запуске модель эмбеддингов и токенизаторы скачиваются из Hugging Face.

5. Построить индекс и проверить его согласованность:

   ```bash
   python source/scripts/load_to_vector_store.py
   python source/tests/check_index.py
   ```

   После изменения данных или параметров существующий индекс пересобирается:

   ```bash
   python source/scripts/load_to_vector_store.py --rebuild
   ```

### Оценка поиска и запуск интерфейса

Для оценки текущего индекса по `questions.json`:

```bash
python source/scripts/evaluate.py
```

Отчёт сохраняется в новой папке внутри `artifacts/evaluation/`.

Для повторения трёх экспериментов и формирования сравнительной таблицы:

```bash
python source/tests/run_experiments.py
```

Этот скрипт работает без доступа к Hugging Face: модель `BAAI/bge-m3`
ревизии `5617a9f61b028005a4858fdac845db406aefb181` должна заранее находиться
в локальном кэше. Нормализованный корпус должен быть подготовлен в `data/cleaned/`.
Скрипт сам обновляет пути между этапами; результаты сохраняются в `experiments/`.

Для запуска интерфейса вопросов и ответов:

```bash
python -m streamlit run source/service/app.py
```

Открыть адрес, выведенный Streamlit в терминале. К этому моменту индекс должен
быть построен, а сервер Ollama — запущен. Настройки модели и бюджета контекста
задаются в секции `llm` файла `config.yaml`.
