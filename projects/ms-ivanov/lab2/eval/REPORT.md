# Шаг 5. Оценка retrieval и подбор параметров индекса

Корпус — 85 документов с тремя звёздами, 255 вопросов (`eval/questions.json`), эмбеддинги BGE-M3,
Qdrant 1.19.2. Все таблицы воспроизводятся командами из последнего раздела.

## Метрики

Чанк **релевантен**, если он из нужного документа и покрывает ≥ 50 % цитаты-ответа (позиции цитат
известны точно, поэтому оценка не зависит от способа разбиения). Для каждого вопроса одна цитата.

| Метрика | Смысл |
|---|---|
| Recall@k (k = 1, 5, 10) | в первых k результатах есть релевантный чанк |
| Precision@k (k = 5, 10) | доля релевантных среди первых k (максимум ≈ 0,2 при k = 5, т. к. релевантен обычно один чанк) |
| MRR | среднее 1 / ранг первого релевантного |
| T-метрики (T1024 … T8192) | ответ найден в первых T токенах выдачи, то есть укладывается в бюджет контекста LLM; нужны для честного сравнения разных размеров чанка |
| ANN recall@10 | (только для HNSW) совпадение приближённого top-10 с точным перебором |

## 1. Размер чанка (3 варианта и более, режим hybrid; вопросы на английском)

| размер | чанков | R@1 | R@5 | R@10 | P@5 | MRR | T1024 | T2048 | T4096 | T8192 |
|---|---|---|---|---|---|---|---|---|---|---|
| 512 | 9070 | 0,584 | 0,902 | 0,965 | 0,180 | 0,725 | 0,788 | 0,890 | 0,965 | 0,976 |
| **1024** | 4494 | **0,682** | 0,957 | 0,976 | 0,191 | **0,798** | 0,671 | 0,839 | 0,957 | **0,976** |
| 2048 | 2398 | 0,667 | **0,961** | **0,988** | **0,192** | 0,787 | 0,067 | 0,671 | 0,859 | 0,965 |
| 4096 | 1468 | 0,663 | 0,945 | 0,988 | 0,189 | 0,786 | 0,039 | 0,153 | 0,733 | 0,914 |

Dense / sparse / hybrid для всех размеров: `eval/chunking-en.md`. Для 4096 dense заметно слабее
(R@1 0,486, MRR 0,642): ответ (~240 токенов) занимает около 9 % чанка, вектор «размывается».

**Вывод:** по R@k большие чанки выглядят лучше только потому, что чанк-мишень больше. При одинаковом
бюджете контекста выигрывают 512–1024; выбран **1024** (лучшие R@1 и MRR, минимум потерь на разрезании
ответов: 98 % цитат целиком в одном чанке против 84 % у 512). При очень малом контексте LLM (≤ 2 тыс.
токенов) лучше 512.

## 2. Режим поиска

| запросы | режим | R@5 | R@10 | P@5 | MRR |
|---|---|---|---|---|---|
| EN | dense | 0,890 | 0,953 | 0,178 | 0,764 |
| EN | sparse | 0,922 | 0,965 | 0,184 | 0,751 |
| EN | **hybrid (RRF)** | **0,957** | **0,976** | **0,191** | **0,798** |
| RU | **dense** | **0,863** | **0,906** | 0,173 | **0,710** |
| RU | sparse | 0,416 | 0,533 | 0,083 | 0,326 |
| RU | hybrid | 0,824 | 0,906 | 0,165 | 0,615 |

Гибрид даёт +6,7 п.п. к R@5 над dense на английском. На русских вопросах (документы английские)
лексический sparse не работает, и слияние ухудшает результат — для них использовать `mode: dense`.

## 3. Параметры HNSW

Данные: 4494 плотных вектора (1024-мерных, cosine), 255 запросов. Опорная точка — точный перебор
(`exact=true`): R@5 0,890, R@10 0,953, P@5 0,178, MRR 0,763. Сетка: `m` ∈ {4, 8, 16, 32, 64} ×
`ef_construct` ∈ {32, 64, 128, 256} × `ef` ∈ {8 … 256} (121 измерение, `eval/hnsw/grid.md`).

ANN recall@10 (`ef_construct` = 128):

| m \ ef | 16 | 32 | 64 | 128 |
|---|---|---|---|---|
| 4 | 0,855 | 0,931 | 0,970 | 0,993 |
| 8 | 0,937 | 0,975 | 0,992 | 0,997 |
| **16** | 0,950 | 0,984 | **0,995** | 0,999 |
| 32 | 0,965 | 0,991 | 0,996 | 1,000 |
| 64 | 0,967 | 0,992 | 0,996 | 0,999 |

* **`ef` важнее всего.** При ANN recall ≥ 0,99 метрики качества совпадают с точным поиском
  (R@10 0,953, MRR 0,763); при `ef` = 16 MRR падает до 0,71–0,75, у слабого графа (`m` = 4,
  `ef_construct` = 16, `ef` = 4) — до 0,45.
* **`m`**: рост от 4 к 16 даёт основную прибавку; после 16 выигрыш в пределах шума, а граф растёт линейно
  (0,3 МБ при `m` = 8; 0,6 МБ при 16; 1,2 МБ при 32; 2,3 МБ при 64 — векторов 18,4 МБ).
* **`ef_construct`**: от 32 к 64 заметный прирост (при `m` = 16, `ef` = 32: 0,964 → 0,984), от 64
  до 256 — в пределах шума. Сборка графа занимает 0,2–0,6 с при любых значениях.
* **Задержка**: p50 одиночного запроса 1,6–3,9 мс для любых настроек, точный перебор — 2,3–3,8 мс.
  Один и тот же точный поиск в разных запусках давал 2,3 и 3,8 мс, то есть шум измерения больше
  разницы между конфигурациями. На 4,5 тыс. векторов HNSW не быстрее перебора; выигрыш по
  скорости появится на корпусе в десятки тысяч векторов и больше (его нужно перепроверить после
  масштабирования той же командой).

**Правило выбора** (`recommend` в `source/indexing/hnsw_report.py`): ANN recall@10 ≥ 0,995 (запас на
рост корпуса), Recall@10 и MRR не хуже точного поиска более чем на 0,5 п.п., `ef` ≤ 64; из подходящих
берётся наименьший граф (`m`), затем наименьший `ef_construct`.

**Выбрано: `m` = 16, `ef_construct` = 64, `ef` = 64.** ANN recall@10 = 0,996, R@5 0,890, R@10 0,953,
P@5 0,178, MRR 0,763 — как у точного поиска. Настройки применены к рабочей коллекции без пересчёта
эмбеддингов (`index-apply`), качество после пересборки графа не изменилось.

### Квантование (`m` = 16, `ef_construct` = 128)

| вектор | rescore | ANN R@10 (ef 64) | R@5 | R@10 | MRR | память под векторы |
|---|---|---|---|---|---|---|
| float32 | – | 0,995 | 0,886 | 0,949 | 0,759 | 18,4 МБ |
| scalar int8 | да | 0,995 | 0,886 | 0,949 | 0,759 | ≈ 4,6 МБ |
| scalar int8 | нет | 0,978 | 0,886 | 0,949 | 0,763 | ≈ 4,6 МБ |
| binary (1 бит) | да | 0,929 | 0,894 | 0,941 | 0,762 | ≈ 0,6 МБ |
| binary (1 бит) | нет | 0,694 | 0,878 | 0,945 | 0,728 | ≈ 0,6 МБ |

Скалярное квантование с rescore не теряет качества и сокращает память в 4 раза; бинарное с rescore
сжимает в 32 раза ценой ≈ 1 п.п. R@10. Сейчас (18 МБ) это не нужно; включать при росте корпуса
(`quantization` в сравнении — `hnsw-bench --quantization scalar binary`).

## Итоговая конфигурация

`configs/default.yaml`: структурный чанкинг, 1024 токена, заголовки в тексте эмбеддинга, BGE-M3
(hybrid; для русских запросов — dense), HNSW `m` = 16, `ef_construct` = 64, `ef` = 64.
Качество: EN hybrid R@5 0,957, R@10 0,976, P@5 0,191, MRR 0,798; RU dense R@5 0,863, R@10 0,906,
MRR 0,710. Запрос — 2–3 мс; индексация корпуса ★★★ (3,2 млн токенов) — около 9 минут на MPS.

## Ограничения

* 255 вопросов: доверительный интервал для Recall около ±2,5 п.п., различия 0,957 vs 0,961 между
  1024 и 2048 несущественны; значимы различия порядка нескольких п.п. (hybrid vs dense, 1024 vs 4096).
* Вопросы синтетические (DeepSeek + ручной отбор), по одному эталонному фрагменту на вопрос.
* HNSW исследован на 4,5 тыс. векторов в Docker-VM (4 CPU): выводы о качестве переносимы, о задержке —
  нет. Перед масштабированием на весь корпус повторить `hnsw-bench` и при ANN recall < 0,995
  увеличить `ef_construct` / `ef`.

## Воспроизведение

```bash
docker compose up -d
.venv/bin/python -m source index                                    # чанки + векторы (configs/default.yaml)
.venv/bin/python -m source index --config configs/chunks-4096.yaml  # и остальные размеры: --set chunking.chunk_size=...
.venv/bin/python -m source index-check --vary chunking.chunk_size=512,1024,2048,4096 --markdown eval/chunking-en.md
.venv/bin/python -m source index-check --lang ru --markdown eval/chunking-ru.md
.venv/bin/python -m source hnsw-bench --name grid                   # сетка HNSW -> eval/hnsw/grid.{md,json}
.venv/bin/python -m source hnsw-bench --m 8 16 32 --ef-construct 128 --ef 16 32 64 128 --passes 10 --name latency
.venv/bin/python -m source hnsw-bench --m 16 --ef-construct 128 --ef 32 64 128 --quantization none scalar binary --name quantization
.venv/bin/python -m source index-apply                              # применить HNSW из конфига к коллекции
```

## Шаг 6. Сквозная проверка RAG (`python -m source rag-eval --n 30 --seed 1`)

30 случайных вопросов из набора; на каждый — полный пайплайн (поиск → промпт → DeepSeek через
`opencode`), затем второй вызов той же модели сравнивает ответ с эталонным (судья). Вызовы строго
последовательные. Данные: `eval/rag/rag-eval.json`.

| показатель | значение |
|---|---|
| вердикт судьи: верно / частично / неверно / нет ответа | 30 / 0 / 0 / 0 |
| нужный фрагмент попал в промпт | 29 из 30 (96,7 %) |
| нужный фрагмент процитирован | 28 из 30 (93,3 %) |
| сниппеты, подтверждённые дословной цитатой | 91,8 % |
| ссылки на несуществующие номера | 1 на 30 ответов |
| среднее время: поиск / LLM | 0,26 с / 6,5 с |

Проверки адекватности: судье подавались заведомо неверный ответ, отказ и посторонний текст — вердикты
`incorrect`, `no_answer`, `incorrect` соответственно, то есть оценка не «штампует» `correct`. Вопросы вне
корпуса («погода в Москве», «чемпион мира 2018») получают отказ без единой ссылки.

Ограничения: судья — та же модель, что отвечает; вопросы синтетические и взяты из самих документов;
выборка мала (при 30 из 30 нижняя граница 95 % интервала ≈ 89 %). Сопоставимые цифры по retrieval — в
разделах 1–3: оценка ответа не заменяет Recall/MRR, а дополняет их.
