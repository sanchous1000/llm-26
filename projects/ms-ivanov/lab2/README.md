# Лабораторная работа №2 — RAG-агент по научным статьям

## Описание задания

Построить RAG-систему по корпусу документов: собрать и нормализовать источники, разбить на чанки,
построить эмбеддинги, загрузить их в векторное хранилище, измерить качество поиска и реализовать движок,
отвечающий на вопросы с цитатами.

**Корпус** — библиографии проекта «Unsupervised Distribution Transfer» (оптимальный транспорт × топологический
анализ данных × генеративные модели): 809 источников в `data/sources.bib` (705 arXiv, 58 журнальных/книжных
по DOI, 29 репозиториев GitHub, 17 веб-страниц) с каталогом приоритетов ★–★★★ в `data/SOURCES.md`.
Для отладки конфигураций выбрано подмножество ★★★ — **85 документов** (≈ 9,1 млн символов, ≈ 5 000
стандартных страниц, 5 840 выносных формул, 432 таблицы). Требование «не менее 50 страниц» выполнено с запасом.

Шаги работы (в скобках — раздел результатов):

1. сбор источников (§1) → 2. разбор в Markdown (§2) → 3. набор вопросов для оценки (§3) →
4. чанкинг, эмбеддинги, БД (§4) → 5. метрики и подбор параметров (§5) → 6. RAG-движок, CLI и MCP (§6).

## Использованные технологии и модели

- **LLM:** DeepSeek `deepseek-v4.1-flash` через CLI `opencode` (генерация вопросов, ответы с цитатами, LLM-судья).
- **Эмбеддинги:** BGE-M3 (мультиязычная, dense 1024 + sparse lexical weights), инференс на Apple MPS (fp16).
- **Хранилища (Docker Compose):** Qdrant 1.19 (векторы, HNSW), PostgreSQL 16 (тексты, метаданные, учёт конфигураций).
- **Сбор и разбор:** requests, BeautifulSoup + lxml, Pandoc (HTML → Markdown), PyMuPDF4LLM (PDF, OCR через Tesseract),
  trafilatura (веб-страницы), bibtexparser.
- **Чанкинг и поиск:** semchunk, transformers/torch, qdrant-client, SQLAlchemy + psycopg, rapidfuzz, pydantic.
- **Интеграция с агентами:** MCP Python SDK (`mcp` 2.x).
- **Качество кода:** pytest (188 тестов, покрытие 90 %), black, ruff; Python 3.14.

## Результаты работы

### 1. Сбор данных

Загрузчики по типам источников: arXiv — HTML с ar5iv/arxiv.org (HTML удобнее PDF: сохраняет разделы, формулы,
таблицы), PDF — как запасной вариант; DOI — открытая копия через OpenAlex и Semantic Scholar; GitHub — README;
веб — страница и PDF по тегу `citation_pdf_url`. Паузы по хостам (для arxiv.org — 15 с по `robots.txt`), повторы,
атомарная запись, возобновляемость.

| тип | всего | скачано |
|---|---|---|
| arXiv | 705 | 705 (691 HTML, 14 PDF) |
| DOI | 58 | 21 (35 — платные книги/статьи без открытой копии, 2 — сбой сети при поиске копии) |
| GitHub / веб | 29 / 17 | 29 / 17 |

### 2. Разбор в Markdown

772 документа → Markdown с YAML front matter (ключ, название, авторы, год, приоритет, теги, исходный файл).
Для arXiv HTML (LaTeXML) написан конвертер: очистка DOM + Pandoc; сохраняются нумерованные заголовки, списки,
теоремы и доказательства, таблицы (pipe-таблицы), формулы как `$…$` / `$$…\tag{n}$$` (TeX берётся из `alttext`
и защищается от экранирования), алгоритмы и код, подписи рисунков, сноски, библиография. Проверка: медиана
сохранности текста HTML → Markdown = 1,00. Итог корпуса: 25,9 тыс. заголовков, 3,4 тыс. таблиц, 51,8 тыс. формул.
Ограничение: в PDF (43 документа) выносные формулы не восстанавливаются.

### 3. Набор вопросов

Для каждого из 85 документов ★★★ модель `deepseek-v4.1-flash` (через `opencode`, строго последовательно) предложила
5 вопросов с цитатой-ответом; цитата проверялась кодом по тексту документа (479 из 480 подтверждены) и получила
точную позицию. Из кандидатов вручную отобрано **255 вопросов** (по 3 на документ: определения, методы, теория,
результаты, сравнения, мотивация) с эталонным ответом и позицией ответа (`eval/questions.json`) — релевантность
чанка считается по пересечению с цитатой, а не по номеру, поэтому метрики не зависят от способа разбиения.

### 4. Чанкинг, эмбеддинги, БД

Сплиттер `structured` режет по смысловым единицам: заголовок неделим со своим текстом, формула — с вводящим
предложением и пояснением «where…», таблица/алгоритм/рисунок — с подписью; разрез сдвигается к границе
теорема/определение/заголовок. В текст для эмбеддинга добавляются название статьи и путь заголовков, библиография
не индексируется. Базовые сплиттеры (`fixed`, `recursive`) и все параметры (размер, overlap, модель, режим
dense/sparse/hybrid, HNSW) задаются конфигом; конфигурации хэшируются и хранятся рядом (набор чанков в
PostgreSQL + отдельная коллекция Qdrant), повторный запуск пропускает неизменённое.
Индексация ★★★ (3,2 млн токенов) — ≈ 9 минут на MPS (≈ 6,5 тыс. токенов/с).

### 5. Метрики и выбор параметров

Метрики: Recall@1/5/10, Precision@5/10, MRR и Recall@T (ответ в первых T токенах выдачи — честное сравнение
разных размеров чанка). Подробности и таблицы — в [eval/REPORT.md](eval/REPORT.md).

**Размер чанка** (hybrid, вопросы на английском, 255 вопросов):

| размер | чанков | R@1 | R@5 | R@10 | P@5 | MRR | найдено в первых 4096 токенах |
|---|---|---|---|---|---|---|---|
| 512 | 9070 | 0,584 | 0,902 | 0,965 | 0,180 | 0,725 | 0,965 |
| **1024** | 4494 | **0,682** | 0,957 | 0,976 | 0,191 | **0,798** | 0,957 |
| 2048 | 2398 | 0,667 | 0,961 | 0,988 | 0,192 | 0,787 | 0,859 |
| 4096 | 1468 | 0,663 | 0,945 | 0,988 | 0,189 | 0,786 | 0,733 |

Ответ занимает ≈ 240 токенов, поэтому крупные чанки «разбавляют» вектор (dense при 4096: R@1 0,49) и уступают
при фиксированном бюджете контекста. Выбрано **1024**. Структурный сплиттер сохраняет ответ целиком в одном
чанке чаще базовых (при 512 токенах: 84 % против 75 % у recursive и 53 % у fixed).

**Режим поиска:** hybrid (RRF) лучше dense и sparse на английском (R@5 0,957 против 0,890 / 0,922); на русских
вопросах работает только dense (R@5 0,863), слияние с sparse ухудшает результат — `mode: auto` выбирает режим
по языку запроса.

**HNSW** (сетка `m` × `ef_construct` × `ef`, 121 измерение, опорная точка — точный перебор): качество равно точному
поиску при совпадении приближённого top-10 с точным ≥ 0,99; основной вклад даёт `ef`, `m` важен до 16,
`ef_construct` — до 64. Выбрано **`m` = 16, `ef_construct` = 64, `ef` = 64** (совпадение с точным поиском 0,996;
R@10 0,953, MRR 0,763 — как у перебора). Квантование: int8 с rescore не теряет качества (память под векторы /4),
бинарное с rescore — ≈ 1 п.п. R@10 (/32).

### 6. RAG-движок, CLI и MCP

Пайплайн: вопрос → эмбеддинг → поиск → пронумерованные фрагменты в промпт (по бюджету токенов) → DeepSeek →
ответ с `[n]` и источниками (статья, раздел, страница, сниппет, ссылка). Сниппет — дословная цитата, найденная
в тексте фрагмента (поэтому не выдуманная); если цитаты нет, подбирается ближайшее предложение с пометкой.

```text
$ python -m source ask "What is the Monge gap and how is it used to learn optimal transport maps?"
The Monge gap is a regularizer that measures how far a given transport map is from being c-optimal …
M(T) = ∫ c(x,T(x)) dρ(x) − W_c(ρ, T♯ρ) … it equals 0 exactly when T is a c-OT map between ρ and T♯ρ [1].
It is added to a fitting loss to learn approximately c-optimal parameterized maps for any cost c [4] …

Sources:
[1] The Monge Gap: A Regularizer to Learn All Transport Maps (Uscidda et al., 2023) — 3 The Monge Gap
    «the Monge gap of a vector field $T:\Omega\rightarrow\Omega$ is defined as:»   https://arxiv.org/abs/2302.04953
[4] … — 4 Learning with the Monge Gap
    «We show how the Monge gap can be used to learn approximately $c$-optimal parameterized maps, for any $c$.»
```

- **CLI** (`ask`, `chat`, `search`): язык ответа — язык вопроса (русский допустим, поиск кросс-языковой); в чате
  история и переписывание уточняющих вопросов (`--condense`); при отсутствии ответа в корпусе модель отказывает
  без ссылок («погода в Москве» — отказ).
- **MCP-сервер** (`python -m source mcp`, stdio / streamable-http) для внешних агентов: инструменты `search_papers`,
  `get_chunk_context`, `list_documents`, `get_document_outline`; агент получает поиск и отвечает своей моделью.
  `python -m source mcp-config` печатает готовую команду/JSON подключения (проверено реальным MCP-клиентом).
- **Сквозная проверка** (30 случайных вопросов, ответ сравнивает с эталоном LLM-судья): верно 30/30; нужный
  фрагмент в промпте — 96,7 %, процитирован — 93,3 %; сниппетов с дословной цитатой — 91,8 %; поиск 0,26 с, LLM 6,5 с.

## Выводы

- **HTML лучше PDF** как источник: структура, формулы и таблицы сохраняются; из PDF формулы теряются.
- **Размер чанка важнее, чем кажется:** большой чанк (4096) даёт высокий «чанковый» Recall только потому, что мишень
  велика; при равном бюджете контекста лучше 512–1024. Выбран 1024; структурное разбиение заметно лучше
  фиксированных окон, потому что не режет формулы, таблицы и ответы.
- **Гибридный поиск** даёт +6,7 п.п. Recall@5 над dense на английских запросах, но для запросов на другом языке
  sparse бесполезен — режим выбирается по языку.
- **HNSW:** на 4,5 тыс. векторов граф не быстрее перебора (≈ 2–3 мс в обоих случаях) — о задержке выводов сделать
  нельзя; качество совпадает с точным поиском начиная с `m` = 16, `ef_construct` = 64, `ef` = 64. После
  масштабирования на весь корпус параметры нужно перепроверить (`hnsw-bench`).
- **Проблемы и решения:** ar5iv отдаёт заглушки «No content available» с кодом 200 (15 статей) — усилена проверка,
  статьи докачаны с arxiv.org или в PDF; быстрый клиент `hf_xet` не проходит через прокси (скачивание весов через
  обычный HTTP); Pandoc портит TeX экранированием — формулы и код подменяются токенами и возвращаются после
  конвертации; модель иногда не пишет заголовок `SOURCES:` — разбор цитат устойчив к этому.
- **Ограничения:** вопросы синтетические (получены моделью из самих документов); LLM-судья — та же модель, что
  отвечает (на 30 вопросах нижняя граница 95 % интервала ≈ 89 %); 37 источников DOI не скачаны (в основном платные; их PDF
  можно положить вручную); индексировано подмножество ★★★ (85 документов), остальной корпус сконвертирован и готов к индексации.

## Инструкция по запуску

Нужны: Python 3.14, Docker (Compose v2), Pandoc, Tesseract (для OCR в PDF, опционально), установленный и
авторизованный `opencode` (для LLM-шагов 3 и 6).

```bash
cd lab2
python -m venv .venv && .venv/bin/pip install -r source/requirements.txt    # + requirements-dev.txt для тестов
cp .env.example .env                       # пароль PostgreSQL и порты
docker compose up -d                       # Qdrant + PostgreSQL

# 1–2. данные (корпус уже лежит в data/papers; команды идемпотентны и пропускают готовое)
.venv/bin/python -m source download && .venv/bin/python -m source convert
# 3. вопросы (уже в eval/questions.json); пересоздать: gen-questions → review-questions → export-questions
# 4. чанкинг + эмбеддинги в PostgreSQL/Qdrant (≈ 10 мин на Apple Silicon)
.venv/bin/python -m source index
# 5. метрики и HNSW
.venv/bin/python -m source index-check --vary chunking.chunk_size=512,1024,2048,4096   # после index для этих размеров
.venv/bin/python -m source hnsw-bench --name grid && .venv/bin/python -m source index-apply
# 6. RAG
.venv/bin/python -m source ask "What is the Monge gap?"      # или: chat, search
.venv/bin/python -m source mcp-config                        # подключение агентов по MCP
.venv/bin/python -m source rag-eval --n 30                   # сквозная проверка

.venv/bin/python -m pytest source/tests -q                   # тесты
```

Варианты размеров для сравнения индексируются так: `python -m source index --set chunking.chunk_size=512`
(и `configs/chunks-4096.yaml`). Справочник по модулям и командам — [source/README.md](source/README.md),
подробные таблицы оценки — [eval/REPORT.md](eval/REPORT.md).
