# Лабораторная работа №2. RAG-агент по материалам НИР

## Описание задания

RAG-агент отвечает на вопросы по материалам научно-исследовательской работы (НИР) по теме ВКР «Анализ методов векторизации текстов для кластеризации статей» и даёт цитаты на источник, раздел и страницу. Пайплайн: исходные документы → нормализованный Markdown → чанки → dense- и sparse-векторы → Qdrant → гибридный поиск → LLM из лабораторной №1 → ответ со ссылками.

### Корпус (шаг 1)

| Тип | Формат | Документы | Объём |
|---|---|---|---|
| Материалы НИР | DOCX | техническое задание; отчёты за семестры I и II; аналитический обзор литературы; список источников; задания на НИР (семестры II, III) | 7 файлов, ≈33 тыс. слов |
| План НИР | XLSX | листы «Семестр I/II/III», таблица гипотез Г1–Г6, календарный план ТЗ (черновики плана семестра III исключены) | 1 файл, ≈2,5 тыс. слов |
| Статьи-источники по гипотезам | PDF (англ.) | Is Anisotropy Truly Harmful?, Pooling and Semantic Shift, REALM, Active Learners as PRP Rerankers, One prompt is not enough, Evolving optimal text clusters, Bayesian semantic structure… | 7 файлов, 122 стр., ≈33 тыс. слов |
| Репозиторий [itmo-research](https://github.com/alinocco/itmo-research) | MD, YAML, PY, SH | README, отчёты, конфиги, исходный код пакета `textvec` | 32 файла, ≈18 тыс. слов |
| **Итого** | | **47 документов** | **≈87 тыс. слов ≈ 290 страниц** |

Исходные документы содержат персональные данные и в репозиторий не коммитятся (`data/` в `.gitignore`).

Оценочный набор — **20 вопросов** (`eval/questions.yaml`): 16 по материалам НИР и репозиторию, 4 по англоязычным статьям (вопрос задаётся по-русски, ответ ищется в английском тексте). Для каждого вопроса есть эталонный ответ, ключевые факты и разметка релевантных мест корпуса (см. шаг 5).

## Использованные технологии и модели

- **LLM:** `qwen2.5:7b` через Ollama (OpenAI-совместимый API) — лучшая модель по итогам лабораторной №1.
- **Dense-эмбеддинги:** `bge-m3` через Ollama (`/v1/embeddings`), 1024 измерения, мультиязычная модель.
- **Sparse-векторы:** BM25 (своя реализация: стемминг Snowball для русского и английского, IDF считает Qdrant).
- **Векторное хранилище:** Qdrant (Docker), HNSW для dense, инвертированный индекс для sparse, гибрид через RRF.
- **Парсинг:** `python-docx` (+ разбор XML для content controls и разрывов страниц), `openpyxl`, `PyMuPDF`.
- **Чанкинг:** `langchain-text-splitters` — `MarkdownHeaderTextSplitter`, `RecursiveCharacterTextSplitter` (в т. ч. `from_language(Language.PYTHON)`); длина считается в токенах `bge-m3` через `tokenizers`.
- **Сервис:** FastAPI + uvicorn, CLI.
- **Анализ:** pandas, tabulate.

### Шаг 2. Парсинг в Markdown

Каждый документ сохраняется в `data/markdown/<doc_id>.md`. В YAML front matter лежат метаданные: `doc_id`, `title`, `source_type`, `format`, `path`, `url`, `date`, `semester`, `page_mode`, `pages`. В тексте сохраняется структура: заголовки h1–h6, списки, таблицы в GFM. Метки страниц оформлены как `<!-- page: N -->`. Сводка корпуса пишется в `manifest.json`.

Нетривиальные места:
- **DOCX без стилей заголовков** (ТЗ, задания на НИР). Заголовки там набраны жирным с номером («**1.1. Предмет работы.**» + текст). Такие строки распознаются эвристикой, уровень заголовка определяется глубиной номера. В документах со стилями эвристика отключена, иначе жирные пункты списков превращались бы в заголовки.
- **Content controls (`w:sdt`).** Отчёт семестра II собран программно, и часть текста лежит в content controls, которые `Paragraph.text` из python-docx пропускает (терялось, например, «≈ 40 мин»). Поэтому текст берётся из всех `w:t` абзаца.
- **Страницы в DOCX.** Используются `lastRenderedPageBreak` (если документ сохранял Word), иначе явные разрывы и `pageBreakBefore`. Если между метками оказывается больше ~1500 слов (то есть разрывы стоят только между крупными частями), номера страниц ненадёжны. Тогда они убираются и цитирование идёт по разделам (`page_mode: none`).
- **PDF.**
  - Заголовки определяются по кеглю и жирности; номер раздела задаёт уровень.
  - Многострочные заголовки склеиваются.
  - Колонтитулы (строки, повторяющиеся на большинстве страниц), водяной знак arXiv и подписи графиков (мелкий кегль) удаляются. Переносы по слогам склеиваются, список литературы отбрасывается.
  - Пробелы в некоторых PDF хранятся отдельными span'ами, их нельзя фильтровать.
- **Имена файлов на macOS** хранятся в NFD («й» = «и» + знак). Все строки приводятся к NFC.
- **Код из репозитория** режется на сегменты по верхнеуровневым `def`/`class` (YAML — по ключам верхнего уровня) и оформляется блоками кода под заголовком с именем функции.

### Шаг 3. Чанки и эмбеддинги

Разбиение выполняют готовые сплиттеры из `langchain-text-splitters`. Своего алгоритма разбиения нет: в качестве `length_function` в них передаётся подсчёт токенов токенизатором `bge-m3`, поэтому `chunk_size` и `overlap` задаются в токенах.

| Сплиттер (`--splitter`) | Реализация |
|---|---|
| `recursive` | `RecursiveCharacterTextSplitter` по всему документу без учёта разделов. Разделители: абзац → строка → предложение → слово |
| `markdown` | `MarkdownHeaderTextSplitter` по заголовкам h1–h3 (`header_levels`): раздел = чанк. Раздел длиннее лимита дорезается `RecursiveCharacterTextSplitter` без перекрытия |
| `hybrid` | `MarkdownHeaderTextSplitter` + `RecursiveCharacterTextSplitter` с перекрытием `overlap` (заголовки + окно/overlap) |

Для файлов кода из репозитория (`.py`) вместо обычного рекурсивного сплиттера используется `RecursiveCharacterTextSplitter.from_language(Language.PYTHON)`: границы ищутся по `class`/`def`.

| Параметр | Флаг | Значения |
|---|---|---|
| сплиттер | `--splitter` | `recursive` / `markdown` / `hybrid` |
| размер чанка, токенов bge-m3 | `--chunk-size` | 100–1000 (по умолчанию 512) |
| перекрытие | `--overlap` | по умолчанию 64 |
| уровни заголовков | `--set chunking.header_levels=N` | по умолчанию 3 (h1–h3) |
| заголовки в тексте для эмбеддинга | `--headers` / `--no-headers` | строка «Документ > Раздел > Подраздел» перед текстом чанка |
| модель | `--dense-model` | `bge-m3` (любая embedding-модель Ollama) |
| тип векторизации | `--vector-type` | `dense` / `sparse` / `hybrid` |

Поверх сплиттеров есть только служебная обработка:
- **Привязка к документу.** Позиция чанка в документе ищется по началу его текста. `start_index` из LangChain бывает −1: при склейке частей сплиттер может заменить разделитель, и чанк перестаёт быть точной подстрокой.
- **Метаданные чанка.** По этой позиции определяются путь заголовков и разделы, которые попали в чанк (для `recursive`), и страницы — по меткам `<!-- page: N -->`, которые затем удаляются из текста.
- **Строка контекста.** К тексту для эмбеддинга добавляется «Документ > Раздел».

**Версионирование.** Артефакты пишутся в `artifacts/<index_id>/`. `index_id` кодирует параметры и хэш корпуса, например `hybrid_cs512_ov64_h1_hybrid_bge-m3_97cdcab2`. Повторный запуск с теми же параметрами ничего не пересчитывает. Смена параметров или перепарсенный корпус дают новую версию рядом. Dense-векторы кэшируются по тексту чанка (`artifacts/_cache/dense.sqlite`), поэтому конфигурации с совпадающими чанками не пересчитываются.

### Шаг 4. Qdrant

Коллекция `nir_<index_id>_m<M>_ef<ef_construct>[_q8]`:
- именованный dense-вектор `dense`: cosine, HNSW `m=16`, `ef_construct=128`; на поиске `hnsw_ef=64`;
- sparse-вектор `bm25` с `modifier=IDF`;
- опционально скалярное квантование int8 (`--quantization scalar`);
- payload: текст, документ, раздел, страницы, путь или URL, дата.

По умолчанию Qdrant не строит HNSW для коллекций меньше 20 МБ и делает полный перебор. Поэтому `indexing_threshold` и `full_scan_threshold` выставлены в 10 КБ (минимум для Qdrant): индекс действительно строится, и параметры HNSW на что-то влияют. На этапе оценки для dense сравнивается выдача HNSW с точным перебором (`ann_agreement@10`).

**Идемпотентность.** id точек — `uuid5(chunk_id)`, повторная загрузка перезаписывает те же точки. Если коллекция уже полная, загрузка пропускается. Флаги: `--rebuild` (он же `--drop-and-reindex`), `--drop`, `--reset-all` (все коллекции с префиксом), `--list`.

### Шаг 5. Метрики

Разметка релевантности не привязана к конкретному чанкингу, поэтому одна и та же разметка годится для всех конфигураций. Для каждого вопроса задаются «группы релевантности» — места в корпусе, описанные через документ, раздел, обязательную подстроку и страницы. Альтернативы внутри группы описывают дубли одного текста: например, ТЗ вложено в приложение отчёта семестра II, а обзор литературы — в отчёт семестра I.

- **Recall@k** — доля групп, покрытых top-k.
- **Precision@k** — доля релевантных чанков в top-k.
- **Hit@k**, **MRR** — по первому релевантному чанку.
- Затраты: время построения индекса, время эмбеддингов, медианная задержка поиска.

Для QA (`eval_qa.py`) считаются:
- **key_fact_recall** — доля ключевых фактов эталона в ответе;
- **citation_precision** — доля процитированных фрагментов, которые релевантны;
- число отказов «нет ответа».

### Шаг 6. RAG-пайплайн

1. Векторизация запроса: bge-m3 и BM25.
2. Гибридный поиск в Qdrant: prefetch dense и sparse, слияние RRF.
3. Сборка промпта: системная инструкция (отвечать только по контексту, ставить ссылки `[n]`, отмечать противоречия источников, при отсутствии ответа отвечать фразой «нет ответа») + вопрос + топ-N фрагментов с источником и местом.
4. Вызов `qwen2.5:7b`.
5. Ответ и цитаты: документ, раздел, страница, сниппет. Номера `[n]` из ответа сопоставляются с фрагментами.

```bash
curl -s localhost:8000/ask -H 'Content-Type: application/json' \
  -d '{"question": "Какие критерии приёмки заданы в ТЗ?", "top_k": 5}'
```

  - q06: таблица в контексте была верной (TF-IDF 0,733 на первом месте), но модель назвала лучшим E5 (0,714). Видимо, её сбила соседняя фраза «лучший результат среди нейросетевых эмбеддингов». Это ошибка чтения таблицы 7B-моделью, а не поиска.
  - a01: 4 из 5 фрагментов контекста — обрывки формул из PDF («P k (nk»). Вывод агент взял из таблицы гипотез НИР, где статья кратко пересказана, а не из самой статьи.

`citation_precision` занижают ссылки на дубли того же текста или соседние разделы, которых нет в разметке: в q04 это раздел о требованиях к корпусу, в q10 — смежные абзацы о методологии обзора.

## Выводы

**Лучшая конфигурация** — E1: hybrid-сплиттер (`MarkdownHeaderTextSplitter` + `RecursiveCharacterTextSplitter`), 512 токенов, перекрытие 64, заголовки в тексте чанка, dense-поиск bge-m3.
- Лучшие Recall@5 (0.875, наравне с E6), Recall@10 (0.925) и MRR (0.784): правильный фрагмент чаще всех стоит первым.
- По затратам это не дороже остальных: один проход эмбеддингов (~2 мин на корпус), BM25 при поиске не нужен.
- Поэтому в `config.yaml` режим поиска по умолчанию — `dense`.
- **E6 (recursive) — близкая альтернатива.** У него та же полнота и лучшая Precision@5 (0.35), а англоязычные статьи он находит лучше всех (0.88). Но MRR ниже (0.721), и он хуже на вопросах о конкретных разделах отчётов (q04).

**Влияние параметров:**
1. **Заголовки в тексте чанка — самый сильный фактор.** Без строки «Документ > Раздел» Recall@5 падает с 0.85 до 0.725, MRR — с 0.720 до 0.637 (E3 → E8). Вопросы часто называют документ или раздел («в ТЗ», «в обзоре литературы», «во втором семестре»), а сам текст чанка этих слов не содержит (q08, q12, q15).
2. **Тип поиска.**
   - Dense (bge-m3) работает лучше BM25 на перефразированных вопросах и находит ответ, когда вопрос на русском, а источник на английском.
   - BM25 в ~8 раз быстрее (5.5 мс против 42 мс; почти всё время dense уходит на векторизацию запроса), но Recall@5 у него всего 0.65.
   - Гибрид через RRF не дал прироста: на русских вопросах он равен dense, а на английских статьях BM25 вытесняет правильные чанки. Гибрид имело бы смысл взвешивать (меньший вес sparse) или включать только для запросов с терминами и кодом.
3. **Размер чанка.**
   - 256 токенов хуже (Recall@5 0.75): таблицы режутся, чанк теряет контекст (q06, q07).
   - 1000 токенов даёт тот же Recall@5, что и 512, но ниже Precision (0.29) и длиннее промпт LLM.
   - Чанк 512 — оптимум.
4. **Сплиттер.** После перехода на LangChain recursive (0.875) обогнал структурные сплиттеры (0.85), хотя в первой версии было наоборот (0.80 против 0.85).
   - **Причина — мелкие разделы.** `MarkdownHeaderTextSplitter` делает каждый раздел отдельным чанком, даже из одной строки. В статье Anisotropy строки формул (`2 )`, `P k (nk`) парсер PDF принял за заголовки. Получились крошечные чанки, текст которых для эмбеддинга почти целиком состоит из названия статьи. На вопрос, где это название упомянуто (a01), они занимают top-5 и вытесняют аннотацию с выводом. `RecursiveCharacterTextSplitter` собирает соседний текст вместе, и проблемы нет.
   - **Почему раньше этого не было.** Первая версия склеивала мелкие разделы, и это маскировало проблему.
   - **Как исправить.** Отбрасывать или присоединять к соседу чанки короче ~30 токенов и ужесточить эвристику заголовков PDF: не считать заголовком строку без букв или из 1–2 символов.
   - **Где структурный сплиттер всё же лучше.** На длинных отчётах он надёжнее: в q04 recursive захватывает в один чанк конец раздела 1.4 и начало 1.5 и проигрывает.
5. **HNSW** на корпусе такого размера не теряет точность (совпадение с точным поиском 100 %). Параметры `M` и `ef` здесь не узкое место.

**Качество ответов.** Агент воспроизводит ключевые факты в 85 % случаев, 15 из 20 ответов полностью верны, ссылки ставятся всегда.

Слабые места и что с ними делать:
- **Ошибки чтения таблиц** (q06). Помогает явное требование в промпте сверять значения в таблице или модель крупнее 7B.
- **Мусорные чанки из PDF** (a01) — см. п. 4.
- **Противоречивая фраза об отсутствии ответа** (a04). Можно ужесточить промпт: отказ только если в контексте нет ничего по вопросу.
- **Неоднозначный вопрос** (q16). Нужно уточнить разметку: добавить второй конфиг как альтернативу или переформулировать вопрос.

**Производительность.** Время ответа (~40 с) почти целиком уходит на обработку промпта: ~2 400 токенов контекста при ~80 ток/с на prefill (как и в лабораторной №1). Генерация занимает 49–315 токенов при ~6 ток/с. Поиск в режиме RAG занимает ~90 мс (медиана). Один раз (q02) он занял 1.9 с: Ollama попеременно держит в памяти bge-m3 и qwen2.5 и в этот момент перезагружала модель. Ускорить ответ можно, если сократить контекст (3 фрагмента или чанки по 256–384 токена в промпте) или взять модель поменьше для простых фактовых вопросов.

**Проблемы и решения:**
- **Потерянный текст в DOCX.** Отчёт семестра II собран программно, и часть текста лежит в content controls. Решение — разбор `w:t` напрямую.
- **Номера страниц в DOCX** ненадёжны (нет `lastRenderedPageBreak`). Для DOCX цитируется раздел, а не страница.
- **Сломанная разметка PDF.** Пробелы хранились отдельными span'ами, а заголовки ACL того же кегля, что и текст. Решение — эвристики по жирности и номеру раздела. Остаточная проблема — строки формул, ошибочно принятые за заголовки (см. вывод 4).
- **Ограничение Qdrant.** Qdrant не принимает `full_scan_threshold` меньше 10 КБ, а по умолчанию не строит HNSW для маленьких коллекций. Порог выставлен в 10 КБ: индекс строится и используется.
- **Самописные сплиттеры заменены библиотечными** (`langchain-text-splitters`).
  - Чтобы размер считался в токенах `bge-m3`, а не в символах, в сплиттеры передаётся `length_function` с токенизатором.
  - `start_index` из LangChain при склейке частей иногда равен −1, поэтому позиция чанка (для раздела и страниц) ищется по началу его текста.
- **Дубли текста в корпусе** (ТЗ в приложении отчёта, обзор внутри отчёта семестра I) учтены в разметке как альтернативы. Иначе Recall наказывал бы за найденную копию.

## Инструкция по запуску

Все команды выполняются из каталога `lab2`.

1. **Окружение:**
   ```bash
   python3 -m venv .venv && source .venv/bin/activate
   pip install -r source/requirements.txt
   ```
2. **Модели Ollama** (Ollama из лабораторной №1 должна быть запущена):
   ```bash
   ollama pull bge-m3
   ollama pull qwen2.5:7b
   ```
3. **Qdrant:**
   ```bash
   docker compose up -d          # дашборд: http://localhost:6333/dashboard
   ```
   Без Docker можно использовать встроенный режим: `--set vector_store.url=path:qdrant_local`. Но HNSW в этом режиме не используется.
4. **Данные.** Документы НИР лежат в `data/raw/`, статьи — в `data/raw/Статьи по гипотезам/`. Репозиторий клонируется так:
   ```bash
   git clone https://github.com/alinocco/itmo-research data/raw/itmo-research
   ```
5. **Парсинг (шаг 2):**
   ```bash
   python source/parse_docs.py
   ```
6. **Индекс (шаг 3) и загрузка в Qdrant (шаг 4):**
   ```bash
   python source/build_index.py                       # параметры из config.yaml
   python source/load_to_vector_store.py              # построит индекс, если его нет, и загрузит
   python source/load_to_vector_store.py --chunk-size 256 --overlap 32   # другая версия
   python source/load_to_vector_store.py --rebuild    # пересоздать коллекцию
   ```
7. **Оценка (шаг 5).** Строит все конфигурации из `experiments.yaml`, это ~20–40 минут из-за эмбеддингов:
   ```bash
   python source/eval_retrieval.py
   python source/eval_qa.py --mode hybrid   # как в отчёте; без флага — dense (лучший по retrieval)
   ```
8. **RAG (шаг 6):**
   ```bash
   python source/ask.py "Сколько документов в корпусе второго семестра?"
   python source/api.py                               # http://127.0.0.1:8000/docs
   ```
