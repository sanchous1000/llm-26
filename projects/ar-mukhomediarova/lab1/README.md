# Лабораторная работа №1. Развёртывание и эмпирический анализ LLM

## Описание задания

Три открытые LLM из разных семейств (Qwen, Llama, Mistral) развёрнуты локально через **Ollama** с OpenAI-совместимым REST API (`http://localhost:11434/v1`). Каждой модели заданы три разнотипных промпта на русском:

| ID | Тип задачи | Суть | Как оценивается автоматически |
|---|---|---|---|
| P1 | Генерация | Вежливое письмо клиенту о задержке заказа (≤150 слов) | доля из 5 обязательных фактов (номер заказа, дата, скидка, промокод, имя), которые попали в письмо без искажений; соблюдение лимита слов |
| P2 | Классификация | 6 обращений → метки `Billing` / `Tech support` / `Sales` | accuracy по эталону; соблюдение формата `<номер>: <метка>` |
| P3 | Извлечение + резюме | Описание смартфона → JSON из 11 полей + `summary` | доля верно извлечённых полей, валидность JSON; поле `warranty_months` в тексте отсутствует (ожидается `null`), поэтому любое значение в нём — галлюцинация |

Каждая комбинация модель × промпт прогоняется в двух режимах и **3 раза** (3 × 3 × 2 × 3 = 54 запроса):

| Режим | `temperature` | `top_p` | `max_tokens` |
|---|---|---|---|
| **A_base** — без изменений | дефолт движка | дефолт движка | дефолт движка (без ограничения) |
| **B_tuned** — тюнинг | 0.2 | 0.8 | 512 |

В режиме A гиперпараметры в запрос не передаются вообще. Фактические дефолты задаются Ollama и Modelfile модели, их можно посмотреть командой `ollama show <model> --parameters`. `top_k` и `repeat_penalty` не меняются, потому что OpenAI-совместимый эндпоинт Ollama их не принимает.

Собираемые метрики:
- **Длина ответа**: `completion_tokens` (среднее и σ по повторам).
- **Точность / адекватность**: `score` из таблицы выше и `format_ok`.
- **Стабильность / детерминизм**: число уникальных ответов среди повторов (`unique_answers`) и средняя попарная похожесть текстов (`similarity`, difflib, 1.0 — полное совпадение).
- **Повторяемость внутри ответа**: доля повторяющихся словесных триграмм (`rep_trigrams`).
- **Галлюцинации**: пропущенные или искажённые факты в P1, `hallucinated_warranty` и неверные поля в P3, ручной просмотр `results/responses.md`.
- **Производительность**: полное время отклика, TTFT (время до первого токена), токены на входе и выходе, скорость обработки входа (`prefill_tps` = входные токены / TTFT) и скорость генерации (`decode_tps`).

## Использованные технологии и модели

- **LLM** (Ollama, квантизация Q4_K_M):
  - `qwen2.5:7b`: Qwen 2.5 7B Instruct (Alibaba)
  - `llama3.1:8b`: Llama 3.1 8B Instruct (Meta)
  - `mistral:7b`: Mistral 7B Instruct (Mistral AI)
- **Сервер инференса:** Ollama (OpenAI-совместимый REST API)
- **Железо:** MacBook Air M3, 16 ГБ
- **Библиотеки:** `openai` (клиент), `pandas` + `tabulate` (агрегация и таблицы)

Структура:

## Результаты работы

Выполнено 54 прогона (3 модели × 3 промпта × 2 режима × 3 повтора), ошибок и обрезанных ответов нет. Все ответы лежат в `results/raw_runs.jsonl` и `results/responses.md`, полные сводные таблицы — в `results/summary.md`. Ниже приведены основные цифры. Кроме автоматических метрик, все ответы просмотрены вручную.

### Скорость и токены

| Модель | Генерация (decode), ток/с | Обработка входа без кэша, ток/с* | Входных токенов в P1 | Токенов на слово ответа (P1, A) |
|---|---|---|---|---|
| qwen2.5:7b | 6.0 | ≈ 85–92 | 219 | 2.6 |
| llama3.1:8b | 5.9 | ≈ 76–78 | 179 | 2.3 |
| mistral:7b | 6.4 | ≈ 61–75 | 230 | 3.3 |

\* Посчитано как входные токены / TTFT для первого («холодного») запроса каждой пары модель × промпт: TTFT составил 2.3–5.3 с. Последующие запросы с тем же промптом Ollama обрабатывает из кэша (TTFT ≈ 0.17 с), поэтому значения `prefill_tps` в `summary.md` (800–1800 ток/с) отражают попадание в кэш, а не реальную скорость обработки входа.

- Скорость генерации у всех моделей практически одинакова (6 ток/с) и **не зависит от режима**: `temperature` и `top_p` влияют только на выборку токена, а не на объём вычислений.
- Время отклика определяется главным образом длиной ответа: письмо (P1) генерируется 34–52 с, классификация (P2) — 4–6 с, JSON (P3) — 18–32 с.
- Токенизатор Mistral хуже всех работает с кириллицей (3.3 токена на слово против 2.3 у Llama), поэтому ответы Mistral такой же длины в словах занимают больше токенов и генерируются дольше. Входные токены Qwen завышены системным промптом, который по умолчанию добавляет его chat-шаблон.

### P1: генерация письма

| Модель | Режим | score (факты) | Слов | Токенов (сред. ± σ) | Похожесть повторов | Время, с |
|---|---|---|---|---|---|---|
| qwen2.5:7b | A | 1.00 | 62–83 | 192 ± 14 | 0.50 | 34.3 |
| qwen2.5:7b | B | 1.00 | 68–80 | 213 ± 12 | 0.58 | 36.7 |
| llama3.1:8b | A | 1.00 | 87–127 | 233 ± 38 | 0.26 | 40.6 |
| llama3.1:8b | B | 1.00 | 103–133 | 254 ± 29 | 0.57 | 43.3 |
| mistral:7b | A | 1.00 | 79–126 | 317 ± 59 | 0.22 | 51.6 |
| mistral:7b | B | 0.93 | 84–99 | 290 ± 17 | 0.41 | 46.1 |

Лимит в 150 слов соблюдён во всех 18 ответах. При ручной проверке нашлось то, что метрика по фактам не ловит:
- **Qwen** во всех 6 ответах выполнил все требования: есть тема, обращение, все факты, ничего лишнего. В режиме B все три темы письма совпали дословно.
- **Llama** в режиме A один раз начал ответ с фразы «Предоставлю вам письмо, согласно описанию:» и один раз пропустил тему. Также добавил от себя утверждение «мы уже нашли решение этой проблемы». В режиме B все три письма начинались с одинаковой темы «Извинения за задержку заказа № 48213».
- **Mistral** не указал тему ни в одном из 6 писем. Один раз выдумал место и дату («Городок, 03.11.2021»), использовал несуществующие слова («Разглезненная», «опытывает») и неуместные обращения («Гражданка Анна Сергеевна» — во всех трёх ответах режима B). В одном ответе режима B пропала новая дата доставки: вместо неё модель посоветовала «проверить состояние заказа в ближайшие дни».

### P2: классификация

| Модель | Режим | Accuracy | Формат | Уникальных ответов из 3 |
|---|---|---|---|---|
| qwen2.5:7b | A / B | 1.00 / 1.00 | 3/3 / 3/3 | 1 / 1 |
| llama3.1:8b | A / B | 1.00 / 0.94 | 3/3 / 3/3 | 1 / 2 |
| mistral:7b | A / B | 1.00 / 1.00 | 3/3 / 3/3 | 1 / 1 |

Задача оказалась простой для всех моделей: строгий формат «номер: метка» соблюдён в 18 из 18 ответов. Даже в базовом режиме все три повтора совпадали побайтно: при коротком и жёстко заданном ответе распределение вероятностей очень острое, и случайность выборки почти не проявляется. Единственная ошибка — Llama в режиме B отнесла обращение №6 («Чем тариф „Бизнес“ отличается… пробный период?») к `Tech support` вместо `Sales`. Это показывает, что `temperature=0.2` без фиксированного `seed` не гарантирует детерминизма.

### P3: извлечение полей и резюме

| Модель | Режим | Доля верных полей | Валидный JSON | Ошибки | Галлюцинация гарантии |
|---|---|---|---|---|---|
| qwen2.5:7b | A | 0.94 | 3/3 | 1 раз `name`/`brand` = «X5»/«Nebula» | нет |
| qwen2.5:7b | B | 1.00 | 3/3 | — | нет |
| llama3.1:8b | A / B | 1.00 / 1.00 | 3/3 / 3/3 | — | нет |
| mistral:7b | A / B | 0.82 / 0.82 | 3/3 / 3/3 | всегда `color: "graphite"`, `price` — объект `{official_store, preorder}` | нет |

- Ни одна модель не заполнила отсутствующее в тексте поле `warranty_months`: все вернули `null`.
- **Qwen** дал самые содержательные резюме на русском. В режиме A один раз неверно разделил название и бренд. Один раз в резюме проскочил артефакт смешения языков: «256 ГБorage».
- **Llama** извлекла все поля без ошибок, но резюме почти бесполезно: в 5 из 6 случаев это «Новинка осени от компании Orion», то есть пересказ первой фразы описания без характеристик.
- **Mistral** систематически нарушает схему: переводит цвет на английский, превращает `price` во вложенный объект и пишет `summary` на английском во всех 6 ответах. Один раз резюме превысило лимит (24 слова при максимуме 20).

## Выводы

**Влияние гиперпараметров** (B: `temperature=0.2`, `top_p=0.8`, `max_tokens=512` против дефолтов):
1. **Стабильность выросла.** Похожесть повторов в P1 увеличилась у всех моделей: Qwen 0.50 → 0.58, Llama 0.26 → 0.57, Mistral 0.22 → 0.41. Разброс длины уменьшился: σ у Mistral 59 → 17 токенов, у Llama 38 → 29. Полного детерминизма нет: в P1 все ответы различались и в режиме B, а в P2 у Llama в режиме B появился один отличающийся (и ошибочный) ответ. Для воспроизводимости нужно дополнительно фиксировать `seed` или ставить `temperature=0`.
2. **`max_tokens=512` на длину не повлиял**: ни один ответ не дошёл до лимита (максимум — 400 токенов). Изменения длины в режиме B вызваны сменой температуры и разнонаправленны: Qwen и Llama стали писать на ~20 токенов длиннее, Mistral — на ~27 короче.
3. **На точность тюнинг почти не влияет.** Случайные ошибки иногда исчезают: перепутанные `name`/`brand` у Qwen в режиме A. Систематические ошибки остаются: схема JSON и английский язык у Mistral, отсутствие темы письма. Низкая температура даже закрепляет неудачные шаблоны: «Гражданка Анна Сергеевна» у Mistral во всех трёх ответах режима B. Систематические ошибки исправляются промптом (примеры, явная схема) или выбором модели, а не параметрами выборки.
4. **На скорость генерации параметры выборки не влияют**: 6 ток/с в обоих режимах. Разница в TTFT между режимами A и B — артефакт порядка прогонов: A шёл первым и попадал на холодный кэш.
5. Повторов внутри ответов почти нет (доля повторных триграмм ≤ 0.017), поэтому для этих моделей и длин `repeat_penalty` не нужен.

**Сравнение моделей:**
- **qwen2.5:7b** — лучший вариант для задач на русском: требования соблюдены во всех задачах, грамотный язык, самые информативные резюме.
- **llama3.1:8b** — точна в извлечении и классификации, но в режиме A хуже следует формату (вступительная фраза, пропущенная тема), а резюме поверхностные. Её токенизатор эффективнее всех на кириллице.
- **mistral:7b** — слабее всех на русском: выдуманные дата и место, несуществующие слова, игнорирование требования о теме, переход на английский в JSON. Генерирует чуть быстрее, но из-за токенизатора и многословности её ответы — самые долгие по времени.

**Проблемы и решения:**
- *Загрузка модели в память искажала бы время первого запроса.* Решение — warm-up запрос перед прогонами каждой модели.
- *Кэш промпта в Ollama.* Повторные запросы с тем же промптом обрабатываются почти мгновенно, поэтому `prefill_tps` по повторам некорректен. Скорость обработки входа оценена по холодным запросам. Для точного замера нужно перемешивать порядок прогонов или сбрасывать кэш (перезагружать модель).
- *`top_k` и `repeat_penalty` нельзя передать через OpenAI-совместимый `/v1`.* Поэтому тюнинг сделан через `temperature`, `top_p` и `max_tokens`. Остальные параметры доступны через нативный API Ollama (`/api/chat`, поле `options`).
- *Автоматические метрики пропускают часть ошибок*: отсутствие темы, язык ответа, качество резюме, выдуманные детали. Поэтому все ответы дополнительно проверены вручную, и выводы о галлюцинациях сделаны по этой проверке.
- *Низкая скорость генерации (~6 ток/с)* заметно ниже типичной для 7–8B Q4 на Apple Silicon. Вероятные причины — троттлинг безвентиляторного MacBook Air при длительной нагрузке и конкуренция за 16 ГБ общей памяти с другими приложениями. Для полной серии из 54 запросов этой скорости хватило.

## Инструкция по запуску

1. Установить Ollama (`brew install ollama` или приложение с https://ollama.com) и запустить сервер:
   ```bash
   ollama serve   # если установлено приложение Ollama, сервер уже запущен
   ```
2. Скачать модели (~4–5 ГБ каждая):
   ```bash
   ollama pull qwen2.5:7b
   ollama pull llama3.1:8b
   ollama pull mistral:7b
   ```
3. Проверить, что OpenAI-совместимый API отвечает:
   ```bash
   curl http://localhost:11434/v1/models
   ```
4. Установить зависимости (из каталога `lab1`):
   ```bash
   python3 -m venv .venv && source .venv/bin/activate
   pip install -r source/requirements.txt
   ```
5. Запустить прогоны. Займёт примерно 15–30 минут, во время работы лучше закрыть тяжёлые приложения:
   ```bash
   python source/run_experiments.py
   # быстрая проверка на одной модели:
   # python source/run_experiments.py --models qwen2.5:7b --repeats 1
   ```
6. Посчитать метрики и собрать таблицы:
   ```bash
   python source/analyze.py
   ```
   Результаты появятся в `results/`.
