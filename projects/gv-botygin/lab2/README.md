# Лабораторная работа №2 — RAG-агент по документации

## Описание задания

Построен RAG-сервис, который отвечает на вопросы по набору PDF-документов и подтверждает ответ цитатами
(документ, страница, раздел, фрагмент текста). Полный путь данных:

```
PDF → Markdown (заголовки h1–h3, таблицы, страницы) → чанки (по заголовкам, затем по токенам)
    → dense-эмбеддинги bge-m3 → Qdrant → поиск → промпт с пронумерованными источниками → LLM → ответ с цитатами
```

Отличия от общего текста задания (по договорённости): формат только PDF, эмбеддинги только dense, LLM — локальная
Ollama из лабораторной работы 1.

## Корпус и вопросы

Пять PDF (94 страницы), каждый документ — ровно один файл в `documents/`:

| Документ | Страниц | Язык | Содержание |
|---|---|---|---|
| `Мини ФС для таролога.pdf` | 28 | рус. | функциональная спецификация AI-таролога (сценарии, API, safety-router, классификатор) |
| `Отчет НИР.pdf` | 36 | рус. | отчёт о НИР: аналитический обзор методов обнаружения дрейфа данных |
| `3448016.3457566.pdf` | 14 | англ. | Xin et al., Production ML Pipelines: Empirical Analysis (Google), двухколоночная статья |
| `Automated_Drift_Detection_and_Retraining_Pipeline_for_ML_Models.pdf` | 5 | англ. | автоматический пайплайн обнаружения дрейфа и переобучения, двухколоночная статья |
| `Learning_with_Drift_Detection.pdf` | 11 | англ. | Gama et al., метод DDM |

Набор из 20 вопросов — `source/eval/questions.json` (8 по таролога, 12 по статьям и отчёту). Для каждого указан
эталон в виде «документ + страницы» (а не ID чанков — поэтому одни и те же вопросы подходят для любых параметров
нарезки) и эталонный ответ. Вопросы русские, три документа английские — это проверяет и кросс-языковой поиск.

## Технологии

- **Парсинг:** `pdfplumber` (текст, таблицы, шрифты)
- **Нарезка:** собственное разбиение по Markdown-заголовкам + `RecursiveCharacterTextSplitter` (`langchain-text-splitters`)
  с длиной в токенах токенизатора модели эмбеддингов
- **Эмбеддинги:** `bge-m3` (локальная папка `models/bge-m3`) через `sentence-transformers`, 1024 измерения,
  cosine, fp16 на GPU (RTX 3070 Laptop)
- **Векторное хранилище:** Qdrant (HNSW с параметрами по умолчанию), `docker-compose.yml`
- **API:** FastAPI + uvicorn
- **LLM:** `qwen3.5:4b` в Ollama (OpenAI-совместимый `/v1/chat/completions`), `reasoning_effort: none`


## Как это работает

**Парсер** (`services/parser.py`). Возвращает Markdown постранично. Заголовки определяются по размеру и жирности
шрифта (три самых заметных стиля → h1–h3), а в научных статьях — по виду строки (`III. METHODOLOGY`, `A. Subsection`);
вложенность «1.», «1.1», «4.4.2» берётся из нумерации. Таблицы — компактный GitHub-Markdown. Двухколоночные страницы
читаются колонка за колонкой (желоб ищется по просвету между словами, широкие строки и заголовки остаются целыми).
Удаляются колонтитулы, номера страниц, оглавление, повёрнутый текст на полях; склеиваются переносы слов; лигатуры
`(cid:N)` превращаются в символы.

**Сплиттер** (`services/splitter.py`). Сначала текст режется по заголовкам h1–h3, затем каждая секция — рекурсивно
по токенам (`chunk_size`, `chunk_overlap`). Путь заголовков `H1 > H2 > H3` добавляется в начало текста чанка (флаг
`include_headers_in_text`, входит в бюджет токенов) и всегда сохраняется в метаданных. Номера страниц протягиваются
через служебные маркеры, поэтому у чанка есть `page_start`/`page_end`. Секции, где «заголовок» — это длинный абзац,
набранный жирным (≥ 60 символов), сохраняются как чанки, а не теряются.

**Индексация** (`scripts/build_index.py`). Один скрипт делает весь путь. Коллекция называется
`{prefix}_{sha1(параметры splitter + embeddings)[:8]}`: смена размера чанка, перекрытия, флага заголовков или модели
автоматически создаёт новую коллекцию, а старая остаётся для сравнения. Документ определяется по имени файла.
ID точки — `uuid5(имя файла : номер чанка)`, поэтому повторная загрузка не плодит дубли. Payload: `text`, `source`,
`path`, `page_start`, `page_end`, `h1`, `h2`, `h3`, `chunk_index`, `indexed_at`, `index_config`.

**RAG** (`services/rag.py`). Запрос векторизуется, ищется `top_k` чанков с `score ≥ score_threshold`, из них
собирается промпт с пронумерованными источниками `[n] (документ, стр., раздел)`. Модель обязана отвечать только по
контексту и ставить ссылки `[n]`; в ответе возвращаются только те фрагменты, на которые она сослалась. Если ничего
не найдено выше порога, LLM не вызывается и возвращается фиксированная фраза.

## Конфигурация (`source/config.yml`)

| Секция | Параметр | По умолчанию | Смысл |
|---|---|---|---|
| `qdrant` | `url`, `collection_prefix` | `http://localhost:6333`, `docs` | подключение и префикс коллекции |
| `embeddings` | `model_name` | `bge-m3` | идентификатор модели, входит в имя коллекции |
| | `model_path` | `models/bge-m3` | папка модели (от `lab2/`) |
| | `device`, `fp16` | `auto`, `true` | `auto` — CUDA при наличии |
| | `batch_size`, `max_seq_length` | `16`, `512` | пакет и усечение входа |
| `splitter` | `chunk_size`, `chunk_overlap` | `300`, `50` | в токенах |
| | `headers_to_split_on` | `[1, 2, 3]` | уровни заголовков |
| | `include_headers_in_text` | `true` | путь заголовков в тексте чанка |
| `search` | `top_k` | `5` | сколько фрагментов брать |
| | `score_threshold` | `0.45` | минимальный cosine score |
| `llm` | `base_url`, `model`, `reasoning_effort`, `temperature`, `max_tokens`, `timeout` | Ollama, `qwen3.5:4b`, `none`, `0`, `500`, `300` | параметры генерации |

Путь к другому конфигу: `--config` у скриптов или переменная `DOC_RAG_CONFIG` у API. Секреты — в `.env`
(`source/.env.example`). Параметры нарезки можно менять флагами скриптов: `--chunk-size`, `--chunk-overlap`,
`--headers-in-text` / `--no-headers-in-text`.

## Запуск

Из корня репозитория (`llm-26`):

```bash
# 1. Qdrant
docker compose -f projects/gv-botygin/lab2/docker-compose.yml up -d

# 2. Зависимости (uv workspace; torch ставится с CUDA-индекса, см. корневой pyproject.toml)
uv sync

# 3. Индексация: существующие документы пропускаются
uv run python projects/gv-botygin/lab2/source/scripts/build_index.py
#    --replace  заменить уже загруженные документы    --reset  пересоздать коллекцию текущей конфигурации
#    --file X.pdf  один документ                      --docs-dir  другая папка с PDF

# 4. Сервис (нужны Ollama с qwen3.5:4b и проиндексированная коллекция текущей конфигурации)
uv run uvicorn doc_rag.app:app --reload      # http://localhost:8000/docs

# 5. Метрики retrieval (результаты -> results/)
uv run python projects/gv-botygin/lab2/source/scripts/evaluate.py --label my_run
```

Если коллекции текущей конфигурации нет, сервис не стартует и сообщает, какой скрипт запустить.

## Результаты

### Метрики retrieval

20 вопросов, чанк релевантен, если документ совпал и его страницы содержат эталонную страницу.

| Конфигурация | chunk / overlap | Заголовки в тексте | Чанков | MRR | Recall@5 | Recall@10 | Hit@10 |
|---|---|:-:|---:|---:|---:|---:|---:|
| MiniLM | 100 / 20 | да | 983 | 0.354 | 0.308 | 0.508 | 0.60 |
| bge-m3 | 150 / 30 | да | 627 | 0.550 | 0.633 | 0.767 | 0.80 |
| bge-m3 | 300 / 50 | нет | 294 | 0.576 | 0.717 | 0.767 | 0.85 |
| **bge-m3** | **300 / 50** | **да** | 310 | **0.640** | 0.700 | 0.825 | 0.95 |
| bge-m3 | 512 / 80 | да | 185 | 0.616 | 0.717 | **0.942** | **1.00** |

Precision@k низкая по построению (на вопрос приходится 1–3 релевантные страницы), поэтому в таблице она не показана.
Поиск вместе с векторизацией запроса занимает 31–37 мс, индексация всего корпуса на GPU — около 14 с.

### Выводы

1. Наибольший вклад далиа модель (MiniLM с окном 128 токенов → bge-m3: 0.60 → 0.95).
   Параметры нарезки влияют слабее.
2. **Заголовки в тексте чанка** улучшают поиск: MRR 0.576 → 0.640, Hit@10 0.85 → 0.95.
3. **Чанки по 150 токенов** хуже: ниже полнота и MRR, а индекс вдвое больше.
4. **512 токенов** даёт лучшую полноту (Recall@10 0.94), но в LLM уходит в ~1,7 раза больше текста, а MRR не лучше.
5. **Выбрана конфигурация 300 / 50 с заголовками**: лучший MRR при компактном контексте. Для `top_k ≥ 10` или reranker
   стоит рассмотреть 512 / 80. Выборка маленькая (одна ошибка = 0.05 по Hit@k), надёжны только крупные эффекты.
6. **`score_threshold`** подобран по распределению top-1 score: релевантные вопросы ≥ 0.49 (медиана 0.61), посторонние
   («Какая столица Австралии?», «Как приготовить борщ?» и др.) ≤ 0.42, поэтому порог 0.45. При прежнем пороге 0.3 посторонние
   вопросы проходили в LLM, и она отвечала «в документах нет информации», тратя ~4 с впустую. Порог подобран на тех же
   20 вопросах и 6 посторонних, его стоит перепроверить на новых данных.

### Примеры ответов `/ask`

Конфигурация 300 / 50, `qwen3.5:4b`, `top_k=5`, `score_threshold=0.45`.

**Вопрос из таролога.** *Какие темы определяет классификатор вопросов таролога и при каком условии возвращается тема other?*

> Классификатор определяет следующие темы: career, love, self, social, health, other [4]. Тема **other** возвращается,
> если уверенность модели в предсказании ниже порога 0.30 [1][3].

| n | Документ | Стр. | Раздел | score |
|---|---|---|---|---|
| 1 | Мини ФС для таролога.pdf | 26 | 4. Спецификация решения … > 4.4 API-функции > Ответ 200 OK | 0.545 |
| 3 | Мини ФС для таролога.pdf | 26 | … > Пример ответа (тема не определена) | 0.477 |
| 4 | Мини ФС для таролога.pdf | 20 | … > ThemeSchemaType | 0.464 |

**Вопрос по английской статье.** *Как метод DDM определяет уровни предупреждения и дрейфа?*

> Уровень предупреждения достигается, если сумма ошибки модели (p_i) и стандартного отклонения (s_i) превышает
> p_min + 2·s_min [1]. Уровень дрейфа фиксируется при превышении p_min + 3·s_min [1].

Цитаты: `Learning_with_Drift_Detection.pdf`, стр. 5 (score 0.577) и стр. 4 (0.565), раздел «3 The Drift Detection Method».

**Вопрос вне корпуса.** *Какая столица Австралии?* — ничего не найдено выше порога, LLM не вызывается:

> В загруженных документах не найдено информации по этому вопросу.

**Промах поиска.** *При какой доле признаков с дрейфом пайплайн автоматического переобучения объявляет условие дрейфа?*
Нужный фрагмент (порог 25 %, `Automated_Drift_Detection…pdf`, стр. 3) в топ-5 не попал, модель честно ответила, что в
найденном такой информации нет, и сослалась на соседний фрагмент отчёта НИР. Это единственный вопрос, не попавший в топ-10 у
выбранной конфигурации 300/50 (при 512/80 фрагмент находится).

## Ограничения

- **Парсер** настроен эвристиками на этот корпус: сканы и картинки не распознаются (на стр. 28 таролога один макет UI,
  текста нет), таблицы без линий (продолжение таблицы 1 в отчёте НИР) читаются как обычный текст по строкам,
  в статье Deshpande блок авторов склеивается беспорядочно.
- Оценка на **20 вопросах** — для окончательных выводов мала; различия между 300 и 512 токенами в пределах шума.
- Корпус содержит пересечения: отчёт НИР пересказывает три других документа, поэтому часть «промахов» — это попадание
  в пересказ, а не в первоисточник.
- Качество ответов `/ask` (полнота, галлюцинации) автоматически не измерялось — оценивался только retrieval.
- Сервис работает синхронно, один процесс; нет истории диалога и фильтра по документу.
