# RAG по документации Kubernetes

Пайплайн: Markdown-источники → чанки → Qwen3-эмбеддинги → Qdrant → glm4:9b
через Ollama → ответ с цитатами. Реализация HTTP-сервиса и CLI находится в `src/rag`.

Оценочный набор: [20 вопросов с ответами и разметкой релевантных чанков](evaluation/README.md),
включая 10 multi-hop.

Код парсера находится в `src/parser`, зависимости — в `requirements.txt`.
Парсер читает локальные Markdown-исходники `kubernetes/website`, раскрывает
поддерживаемые шорткоды Hugo, копирует локальные картинки и сохраняет
нормализованный Markdown вместе с JSON-метаданными. LLM не требуется.

### Запуск

Команды выполняются из `projects/ad-shinyakov/lab2`:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

git clone --depth 1 --branch release-1.35 \
  https://github.com/kubernetes/website.git /tmp/kubernetes-website

PYTHONPATH=src python -m parser \
  --repo /tmp/kubernetes-website \
  --section docs/concepts \
  --base-url https://v1-35.docs.kubernetes.io \
  --output data/kubernetes
```

Для небольшого запуска добавьте `--limit 10`. Для нескольких разделов повторите
`--section`. Язык выбирается через `--language` (по умолчанию `en`).
Коммит исходников фиксируется в метаданных; для воспроизводимости используйте
checkout конкретного коммита.

### Устройство

- `RepositorySource` — поиск исходников, чтение front matter через
  `python-frontmatter` и сведений Git.
- `ShortcodeProcessor` — раскрытие figure, примеров кода, glossary, ссылок,
  feature-state и примечаний; неизвестные конструкции сохраняются с предупреждением.
- `DocumentParser` — организация обработки документа и сохранение метаданных.
- `parser/markdown.py` — Mistune разбирает Markdown и записывает его через
  `MarkdownRenderer`; BeautifulSoup обрабатывает HTML-вставки изображений.
- `ImageStore` — копирование локальных картинок с именами по хешу.
  Внешние картинки остаются ссылками. Распознавание изображений не выполняется.
- `FileStorage` — сохранение файлов.
- `ParsingPipeline` — обработка выбранных документов и запись manifest.

Результаты находятся в `data/kubernetes/documents`, изображения — в `assets`,
сводка — в `manifest.json`. Подписи, alt и окружающий текст сохраняются.
Повторный запуск перезаписывает результаты выбранных документов и manifest,
но не удаляет старые файлы, не вошедшие в новый запуск.
Код завершения `1` означает ошибки или предупреждения; подробности находятся
в manifest и JSON документов. Успешный запуск возвращает `0`.

## Автоматическое скачивание

Без `--repo` модуль сам клонирует `kubernetes/website` из GitHub:

```bash
PYTHONPATH=src python -m parser --ref release-1.35 --limit 10
```

Нужны установленный `git` и доступ к GitHub. `--ref` принимает ветку или тег;
по умолчанию используется `release-1.35`. Копия сохраняется в `data/sources`
(путь меняется через `--cache`) и используется повторно без обновления.
Для получения свежего состояния ветки укажите новую папку кеша.
Для локального репозитория по-прежнему используется `--repo`.

## Чанкирование

`ExperimentalMarkdownSyntaxTextSplitter` разделяет Markdown по H1–H3 и
выделяет код в отдельные фрагменты, сохраняя отступы. Внутри фрагмента
`RecursiveCharacterTextSplitter` выполняет разбиение с токенизатором Qwen.
По умолчанию `chunk_size=800`, `overlap=100`, `include_headings=False`.

Заголовки сохраняются в `heading_path`, но не добавляются к `text` чанка.
Эмбеддинги строятся только по содержимому. Заголовки можно добавить к контексту
LLM после поиска. `--no-headings` явно выбирает это поведение.

```bash
PYTHONPATH=src python -m chunker \
  --input data/kubernetes \
  --output data/chunks \
  --chunk-size 800 --overlap 100
```

`--tokenizer` меняет токенизатор (по умолчанию Qwen3-Embedding-0.6B).
При первом запуске загружаются только файлы токенизатора, без весов модели.
Результаты сохраняются в `data/chunks/<версия>/chunks.jsonl` и `manifest.json`.
Настройка заголовков входит в конфигурацию версии; старые результаты не меняются.

`--splitter markdown` (по умолчанию) использует разделение по H1–H3,
`--splitter recursive` разбивает весь исходный текст без учёта заголовков.
Во втором режиме исходные заголовки остаются частью Markdown; `heading_path`
содержит только название документа, а язык отдельных блоков кода не выделяется.
Стратегия сохраняется в config и manifest и влияет на версию результатов.

В Markdown-режиме соседние фрагменты с одинаковым `heading_path` получают общий
`section_id`; `section_part` и `section_parts` считаются по всем чанкам группы.
Одноимённые соседние разделы могут объединиться: точные границы их исходных
вхождений библиотека не возвращает. Overlap остаётся внутри каждого фрагмента,
а не переносится с объяснения на отдельный блок кода.

`strip_whitespace=False` сохраняет крайние отступы. Ограждения длинного кода
после разрезания не восстанавливаются; язык хранится в `code_language`.
`--headings` добавляет путь заголовков в текст; его длина вычитается из бюджета,
при необходимости overlap уменьшается. По умолчанию заголовки только в metadata.
Библиотечная сборка суммирует длины частей, поэтому возможен небольшой выход
за лимит при повторной токенизации готовой строки (например, 801 вместо 800).
Строгая финальная коррекция по токенам пока не выполняется.

## Эмбеддинги и Qdrant

Нужен Python 3.10+ и зависимости из `requirements.txt` (проверка выполнялась на
Python 3.12). Команды ниже выполняются из папки лабораторной.

### 1. Построение эмбеддингов

```bash
python scripts/build_embeddings.py \
  --input data/chunks/82bc0715187c1fbe \
  --output data/embeddings \
  --batch-size 8
```

Путь входа замените на нужную версию чанков. Эквивалентная точка входа:
`PYTHONPATH=src python -m embedder ...`.

По умолчанию используется `Qwen/Qwen3-Embedding-0.6B` через SentenceTransformers.
Это отдельная модель эмбеддингов: в отличие от чанкирования, теперь скачиваются
и веса модели. Устройство выбирает библиотека; явно можно указать
`--device cpu`, `--device mps` (Apple Silicon) или `--device cuda`.
При нехватке памяти уменьшайте `--batch-size`.

Параметры:

- `--model`, `--revision` — модель и ревизия Hugging Face. Ветка `main` разрешается
  в конкретный коммит, который сохраняется в manifest.
- `--max-length 2048` — лимит входа модели. Превышение вызывает ошибку, а не
  незаметное усечение текста. Чанки 800 токенов обычно помещаются с запасом.
- `--dimensions` — необязательное сокращение вектора; используйте только с
  моделями, поддерживающими усечение размерности (например, Qwen3/MRL).
- `--document-prefix`, `--query-prefix` — формат входа документов и запросов.
  У Qwen3 документы идут без инструкции, запрос получает инструкцию поиска.
  При смене семейства модели задайте префиксы согласно её model card.
- `--rebuild` — повторно вычислить существующую версию.

Векторы записываются как нормализованный `float32`. Нормализация выполняется
после возможного сокращения размерности. Исходные чанки копируются в артефакт
без изменения порядка. Батчинг выполняет SentenceTransformers. Готовая матрица векторов собирается
в оперативной памяти и сохраняется через `np.save`: для небольшого корпуса
это проще собственной записи по батчам. При загрузке в Qdrant файл по-прежнему
читается через mmap.

```text
data/embeddings/<версия>/
├── vectors.npy
├── chunks.jsonl
└── manifest.json
```

Версия определяется содержимым чанков, manifest чанкирования, конфигурацией
кодирования и коммитом модели. Manifest содержит размерность, количество строк,
контрольные суммы файлов, настройки чанкирования и формат запросов. Повторный запуск
проверяет файлы и использует готовый результат. Сборка идёт во временной папке:
незавершённое вычисление не публикуется как готовая версия. При прерывании
вычисление начинается заново; загрузку в Qdrant можно повторять независимо.

### 2. Запуск Qdrant

```bash
docker compose up -d
```

В Compose закреплена версия `qdrant/qdrant:v1.19.2`. Данные сохраняются в
`qdrant_data`, HTTP API доступен на `http://localhost:6333`, интерфейс —
`http://localhost:6333/dashboard`. Порты опубликованы только на localhost.

### 3. Загрузка

Подставьте путь, напечатанный построителем эмбеддингов:

```bash
python scripts/load_to_vector_store.py \
  --input data/embeddings/<версия> \
  --url http://localhost:6333 \
  --m 16 --ef-construction 128 --ef-search 128 \
  --batch-size 128
```

Эквивалентная точка входа: `PYTHONPATH=src python -m vector_store ...`.
Для облака можно задать `QDRANT_URL` и `QDRANT_API_KEY` в окружении.

Выбранные решения:

- Именованный вектор `dense`, метрика `Cosine`; размерность берётся из артефакта.
  Квантование пока отключено для оценки исходного качества.
- Одна точка на чанк; UUIDv5 получается из `chunk_id`. В payload хранится весь
  чанк, а также `chunk_id` и версия эмбеддингов. Payload-индексы по `document_id`,
  `section_id`, `chunk_id` позволяют фильтровать связанные фрагменты.
- `m=16` задаёт связность HNSW, `ef_construct=128` — бюджет построения.
  Это стартовые параметры для эксперимента, не гарантированный оптимум.
- `--ef-search` сохраняет рекомендуемый `hnsw_ef` в upload manifest;
  при запросах параметр реально применяет класс `VectorSearch`. Он не является
  настройкой построения коллекции и не входит в её имя.
- Автоматическое имя `kubernetes_<hash>` учитывает версию и контрольные суммы
  эмбеддингов, размерность, метрику и HNSW. Другая модель, корпус или настройки
  построения создают отдельную коллекцию; старые коллекции не удаляются.
- Идентичность данных хранится в metadata коллекции. При `--collection NAME`
  загрузчик проверяет совместимость и отказывается смешивать разные версии.
- Пакетный `upsert(..., wait=True)` позволяет повторять загрузку без дубликатов
  и продолжить после сбоя. После загрузки проверяется точное количество точек.

Для полного reset и повторной загрузки выбранной коллекции:

```bash
python scripts/load_to_vector_store.py \
  --input data/embeddings/<версия> \
  --collection kubernetes_example \
  --drop-and-reindex
```

`--rebuild` — синоним `--drop-and-reindex` у загрузчика. Указанная коллекция
удаляется целиком. Если имя не задано, пересоздаётся вычисленная коллекция этой
конфигурации. Обычный повторный upsert не удаляет посторонние точки: если они
обнаружены по несовпадению количества, загрузчик требует reset.

Результат записывается рядом с эмбеддингами в `upload_manifest_<hash>.json`:
коллекция, количество точек, версия эмбеддингов, параметры построения/поиска,
состояние коллекции, число проиндексированных векторов и время загрузки.
Небольшой корпус может обслуживаться полным перебором: HNSW строится Qdrant
асинхронно при достижении порога индексации. Успешная загрузка не утверждает,
что граф уже построен. `VectorSearch` поддерживает фильтр и число результатов;
LLM и multi-hop цикл в этом модуле не реализуются.

### Проверки

```bash
PYTHONPATH=src python -m unittest discover -s tests -v
```

Тесты работают с детерминированным тестовым энкодером и встроенным Qdrant,
без загрузки весов и Docker. Они проверяют версии, кеш, повреждения артефактов,
повторную загрузку, несовместимые конфигурации, reset, возобновление частичной
загрузки, фильтры и поиск. Встроенный Qdrant не проверяет серверную индексацию HNSW.

Серверный тест (создаёт и удаляет отдельную коллекцию `rag_test_<uuid>`):

```bash
QDRANT_TEST_URL=http://localhost:6333 PYTHONPATH=src \
  python -m unittest discover -s tests -v
```

Для полного корпуса построены эмбеддинги 2950 чанков и выполнено
[сравнение конфигураций этапов 3–4](evaluation/retrieval/embedding_dimensions/report.md).
Автоматические тесты включают проверку RAG, цитирования и HTTP API;
серверный тест включается отдельно через QDRANT_TEST_URL.

## Пункт 6: RAG-сервис

Используется LLM из первой лабораторной: **glm4:9b через Ollama**.
Для retrieval выбрана 1024-мерная конфигурация из пункта 5: Markdown 800/100,
Qwen3-Embedding-0.6B, Cosine, HNSW M=16, ef_construction=128, ef_search=128.
Сервис использует готовую коллекцию и не перестраивает индекс при запуске.

Установите обновлённые requirements и убедитесь, что Ollama и Qdrant запущены:

```bash
python -m pip install -r requirements.txt
docker compose up -d
ollama list
```

Если glm4:9b ещё нет в Ollama: `ollama pull glm4:9b`.
Команды дальше выполняются из `projects/ad-shinyakov/lab2`.

### HTTP API

```bash
python scripts/ask.py \
  --embeddings data/embeddings/72ae1550489b20f9 \
  --collection eval_config_4f81592daeca8af76b57 \
  --llm-model glm4:9b \
  --serve
```

```bash
curl http://127.0.0.1:8000/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"Чем ReadWriteOnce отличается от ReadWriteOncePod?","top_k":10}'
```

`GET /health` проверяет, что процесс и пайплайн инициализированы; доступность
LLM проверяется фактическим запросом, этот endpoint не генерирует ответ.
Swagger: `http://127.0.0.1:8000/docs`. Сервер слушает localhost.
Состояние моделей загружается один раз на процесс, обращения сериализованы,
чтобы два запроса не запускали конкурирующие вычисления на одной GPU.

### Один вопрос или интерактивный режим

```bash
python scripts/ask.py \
  --embeddings data/embeddings/72ae1550489b20f9 \
  --collection eval_config_4f81592daeca8af76b57 \
  --question 'Чем ReadWriteOnce отличается от ReadWriteOncePod?'
```

Для интерактивного режима уберите `--question`; выход — `/exit`.
Вопросы обрабатываются независимо: история диалога не хранится.
`--json` выводит машинный ответ. Эквивалентный запуск модуля:
`PYTHONPATH=src python -m rag ...`.

Пути выше соответствуют завершённому эксперименту в этой рабочей копии.
Для другой сборки задайте её embedding bundle и совместимую коллекцию.
Проверяются хеши артефактов, идентичность модели/данных/индекса и количество точек;
запрос кодируется в той же ревизии модели, размерности и с тем же префиксом,
что сохранены в manifest эмбеддингов.

### Как устроен запрос

1. `retriever.py` векторизует исходный вопрос через Qwen и ищет чанки в Qdrant.
   При пустой выдаче возвращается отказ без вызова LLM.
2. `pipeline.py` запрашивает `SearchPlan`: 1–4 атомарные подзадачи и английские
   поисковые запросы. Если пользователь явно задал 2–4 вопросительных предложения,
   а также явные части вида «и как…» или «и на какой…», код сохраняет
   их дословно и в том же порядке: модель формулирует запросы,
   но не может выбросить вопрос или заменить его проверкой уже заданного условия.
   Модель не обязана дословно воспроизводить вопросы: исходные формулировки
   подставляет код, а объединение или добавление подзадач отклоняется.
   Идентификаторы подзадач назначает код. На этой стадии ответа нет.
3. `prompt.py` собирает запрос извлечения: исходный вопрос, план, целые чанки,
   известные свидетельства и незакрытые подзадачи. `SearchStep` содержит точные
   цитаты с requirement_id/source_id и предложение следующего поискового запроса.
   Поля answer на этой стадии нет. Модель может найти свидетельства для нескольких
   подзадач за один поиск; обязательного второго поиска нет.
4. `evidence.py` проверяет номера подзадач и источников, ищет цитаты дословно
   (допускается различие пробелов и переносов). Сохраняет исходный фрагмент,
   chunk_id и span_start/span_end — индексы Unicode-символов в исходном чанке.
   Цитата расширяется до границ абзаца, чтобы сохранить условия и подписи
   вроде `Delete` у Markdown definition list.
   Цитаты одной подзадачи из одного чанка объединяются в непрерывный фрагмент
   от начала первого абзаца до конца последнего. Это сохраняет определения и
   значения по умолчанию вместе. При расширении фрагмента прежний вердикт
   снимается, требуется новая проверка.
   Выдуманные цитаты отклоняются и отражаются в rejected_evidence.
5. С экспериментальным флагом `--verify-evidence` для каждой подзадачи с новыми
   цитатами выполняется отдельный `EvidenceReview`. По умолчанию он выключен: glm4
   на диагностических примерах отвергала и достаточные цитаты, включая Service.
   В question получает текущую подзадачу; полный вопрос передаётся отдельно в
   original_question, поисковая формулировка — в lookup_query. Получает дословные
   абзацы с заголовками источников. Сначала составляет короткий answer из правил
   и исходных условий, затем оценивает достаточность. Готового финального ответа
   и прежнего вердикта в этом запросе нет. Числа и настройки из вопроса не нужно
   повторно искать в документации. Примеры различают триггер операции, обновление
   конфигурации и правила удаления разных ресурсов.
   Возвращает answer, status (`supported`, `partial`, `unsupported`), source_ids, reason,
   missing_information и next_query. Только `supported` с существующими цитатами
   закрывает подзадачу. Остальные кандидаты не попадают в финальный ответ.
   Без этого флага сохраняется прежний режим: достаточно дословной цитаты,
   выбранной извлекателем, смысловая достаточность отдельно не проверяется.
   Неподтверждённые цитаты остаются в трассе для диагностики.
6. Пока остались незакрытые подзадачи, выполняется новый поиск: сначала уточнение
   проверяющего, затем ещё не выполненный запрос плана, затем уточнение извлекателя.
   Источник выбора запроса отражён в next_query_origin (`critic`, `plan`, `model`).
   `next_query=null`, повтор запроса и отсутствие новых чанков не доказывают полноту.
   Чанки накапливаются без повторов; число поисков ограничено max_hops.
7. Финальный `DraftAnswer` генерируется отдельным вызовом только по принятым
   цитатам и исходному вопросу. Содержит answer и source_ids. Полные необработанные
   документы и выдуманные свидетельства в этот вызов не передаются.
8. Проверяются номера ссылок. URL, раздел и snippet копируются кодом, snippet
   теперь является проверенной цитатой, а не всем чанком. Если в финальном
   ответе отсутствуют ссылки для какой-либо подзадачи, выставляется
   insufficient_context=true и добавляется перечень неподтверждённых вопросов.
   Если после поиска подзадачи остаются незакрытыми, свободная финальная генерация
   пропускается: возвращаются только реальные цитаты и список пробелов.
   При отсутствии свидетельств возвращается отказ без финальной генерации.

`llm.py` передаёт соответствующую JSON schema для каждой стадии в Ollama.
Некорректный JSON или неверные финальные ссылки повторяются один раз.
Опция `--verify-answer` добавляет проверку финального ответа той же моделью
по тем же цитатам. По умолчанию выключена; гарантией достоверности не является.

Формат API сохранён: question, answer, citations, insufficient_context, metadata.
В metadata находятся requirements, missing_requirement_ids, evidence с позициями,
evidence_reviews с последними вердиктами, stop_reason и hops с запросами,
кандидатами, отклонёнными цитатами и reviews с usage каждого проверяющего.
usage.planning и usage.answer содержат вызовы планирования и финального ответа;
usage промежуточных извлечений лежит в hops; проверки — в hops[].reviews[].usage. Попытки исправления JSON учитываются.
context_chunk_ids соответствует номерам источников финального промпта.
Одинаковый абзац из одного чанка передаётся один раз с requirement_ids всех
подзадач, для которых он был выбран; это устраняет дубли и лишние ссылки.
Разные абзацы одного чанка могут остаться отдельными источниками.

Происхождение цитат проверяется кодом, смысловая достаточность — отдельным
вызовом той же glm4:9b при `--verify-evidence`. Это не независимая модель и не гарантия корректности: проверяющий
может повторить ошибку извлекателя. Ошибки декомпозиции,
нерелевантные настоящие цитаты и неверный синтез всё ещё возможны. Наличие
двух поисков само по себе не является критерием правильности ответа.

HTTP-коды: 422 — неверное тело запроса, 400 — превышен бюджет входа,
502 — некорректный ответ LLM, 503 — недоступен backend, 504 — timeout LLM.

### Настройки

- `--llm-model`, `--ollama-url`, `--timeout`: модель и адрес Ollama, timeout по умолчанию 180 с.
- `--max-hops` (3, допустимо 1–5): предел числа поисков. При 1 выполняется
  один поиск, но сохраняются стадии планирования, извлечения и ответа.
  Без проверки свидетельств и повторов максимум вызовов LLM —
  план + max_hops извлечений + ответ (5 при max_hops=3).
  С `--verify-evidence`, без повторов и опциональной проверки ответа, максимум:
  план + max_hops × (извлечение + до 4 проверок подзадач) + ответ,
  то есть до 17 при max_hops=3. Проверка выполняется только при новых кандидатах
  для ещё незакрытой подзадачи. Пустые выдачи и отсутствие новых чанков сокращают
  число вызовов. `--top-k` применяется к каждому поиску.
- `--top-k` (10), `--ef-search` (128), `--min-score` (0.5): поиск.
  Порог 0.5 проверен на текущих 20 оценочных вопросах: retrieval-метрики не изменились.
  На проверочном вопросе вне корпуса он отсекает все совпадения, и LLM не вызывается.
  Это эвристика для текущей модели/корпуса, а не вероятность правильного ответа;
  при смене модели порог нужно пересмотреть. `--min-score -1` отключает отсечение.
- `--context-window` (32768), `--max-tokens` (1024): окно LLM и выход.
  Вход считается через `AutoTokenizer.from_pretrained("zai-org/glm-4-9b-chat-hf")`
  из transformers, ревизия закреплена в `rag/tokenizer.py`. Токенайзер загружается
  один раз и использует `apply_chat_template(messages, tokenize=True,
  add_generation_prompt=True)`: учитываются роли, служебные токены и все тексты.
  Загрузка выполняется с `trust_remote_code=False`, веса LLM не скачиваются.
  При первом запуске нужен доступ к Hugging Face, затем используются файлы кеша.
  При отборе чанков и перед генерацией проверяется:
  `input_tokens + max_tokens <= context_window`. Автообрезание отключено;
  фактический `prompt_eval_count` дополнительно сверяется с предварительным.
  Повторная проверка также подбирает цитаты с учётом полного бюджета промпта.
  Для другой LLM нужно выбрать совместимый токенайзер и шаблон в `rag/tokenizer.py`.
  Подсчёт выполняется локально, без HTTP-запросов к Ollama.
  Совпадение с glm4:9b проверено на русском тексте, YAML и Unicode: 16/30/21 токен.
- `--device`, `--host`, `--port`: устройство эмбеддера и адрес API.
- Переменные окружения: `LLM_MODEL`, `OLLAMA_URL`, `QDRANT_URL`, `QDRANT_API_KEY`.

### Сквозная проверка и ограничения

При запущенном API:

```bash
python scripts/smoke_rag.py --embeddings data/embeddings/72ae1550489b20f9
```

Скрипт сохраняет реальные HTTP-ответы и report.md, проверяет источник каждого
сниппета по embedding bundle, обычный вопрос, составной DNS-вопрос и отказ
на вопрос вне корпуса. Ненулевой exit code означает провал хотя бы одного сценария.

Сравнение сохранённых ответов находится в [evaluation/rag](evaluation/rag/README.md):
однопроходный RAG, повторная проверка ответа, поиск по плану, проверка свидетельств
и вариант с обновлёнными промптами. Сохранены реальные ответы и неудачные случаи.
Это диагностические прогоны, а не полная QA-оценка на 20 вопросах. Service отвечает
верно; на ConfigMap и StatefulSet/PVC остаются ошибки достаточности цитат и синтеза.
`--verify-evidence` остаётся экспериментальным и выключенным по умолчанию.

Сравнение retrieval: [размерности эмбеддингов](evaluation/retrieval/embedding_dimensions/report.md),
[методы поиска](evaluation/retrieval/search_methods/report.md),
[инструкции запросов](evaluation/retrieval/query_instructions/report.md).
Порог 0.5 проверен отдельно: [score_threshold.json](evaluation/retrieval/score_threshold.json).

Новые прогоны сохраняются в игнорируемый `evaluation/local_runs/`.
Для проверки промпта REVIEW есть `scripts/evaluate_evidence_review.py` и
`tests/fixtures/evidence_review_cases.json`; результаты этой диагностики сохраняются
в игнорируемый `data/experiments/evidence_review/`.
Промежуточные трассы и старые технические проверки сохранены локально в
`data/evaluation_archive/before_cleanup_2026-11-01/` и не входят в Git.

Теперь используется multi-hop retrieval с планом подзадач и проверкой точных цитат.
Граф не строится; цикл использует существующие Qdrant, Pydantic и Ollama.

Документация выбранных API: [Qwen3 Embedding](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B),
[коллекции Qdrant](https://qdrant.tech/documentation/manage-data/collections/),
[идентификаторы и upsert](https://qdrant.tech/documentation/concepts/points/).


Обёртка Markdown упрощена: номера строк, генерация якорей и служебные маркеры
заголовков удалены. В метаданных остаются путь заголовков и ссылка на документ.
Используется `ExperimentalMarkdownSyntaxTextSplitter`: он сохраняет пробелы
и переносы строк без собственной защиты кода. `code_blocks.py` удалён.
Сплиттер выделяет код в отдельные фрагменты с тем же путём заголовков;
язык сохраняется в `code_language` метаданных чанка. Горизонтальные разделители
также образуют границы фрагментов. Каждый возвращённый фрагмент обрабатывается
отдельно, overlap между ним и соседним фрагментом не добавляется.
Повторяющиеся заголовки обрабатываются по стандартным правилам библиотеки.
Класс экспериментальный: при обновлении зависимости стоит проверить поведение.
Метод `_split_section()` настраивается пользователем.


Чанкировщик работает напрямую с библиотечными `Document`: классы-обёртки
`Section` и `MarkdownSections` и файл `chunker/markdown.py` удалены.
Метод `_sections()` выбирает библиотечную стратегию, `_split_section()` задаёт
размеры, `_make_chunk()` собирает метаданные. Конфигурация и имя токенизатора
сохраняются один раз в manifest; в каждой строке chunks.jsonl они не дублируются.
Источники, иерархия, section_id и соседние ID остаются в чанках.


Эмбеддер использует библиотечные `batch_size`, `normalize_embeddings` и
`truncate_dim` вместо ручного батчинга, усечения и нормализации. Полный manifest
чанкирования не дублируется: сохраняются его хеш и конфигурация. Проверки
артефактов, фиксация коммита модели, кеш и временная папка сборки остаются.
Версия алгоритма обновлена, поэтому старые артефакты не перезаписываются.


## Библиотечная нормализация Markdown

Чтение и запись YAML front matter выполняет `python-frontmatter`. Синтаксис
ссылок, изображений, таблиц, списков, inline-кода и блоков кода разбирает Mistune
3.4+. Собственные регулярные выражения для Markdown-ссылок и ручное отслеживание
границ fenced-кода удалены. Reference-ссылки преобразуются в обычные ссылки;
внешние URL, включая скобки, сохраняются целиком. Относительные адреса обычных
ссылок преобразуются в опубликованные URL, пути локальных картинок — в assets.

Для Hugo остаётся отдельный обработчик. Первый проход Mistune временно маскирует
только открывающие последовательности шорткодов внутри кода, затем раскрываются
настоящие шорткоды, маски снимаются и второй проход нормализует ссылки и картинки.
Примеры шорткодов и ссылок внутри кода не выполняются и не переписываются.
HTML-комментарии удаляются, неизвестные шорткоды сохраняются с предупреждением.
Это ограниченный набор поддерживаемых шорткодов, а не полная замена движка Hugo.

Форматирование Markdown может нормализоваться (например, маркировка списков и
форма ссылок). Содержимое YAML, вложенность списков и таблицы проверяются тестами.
Команды запуска и структура выходных файлов прежние; перед запуском обновите
зависимости: `python -m pip install -r requirements.txt`.

Проверено 8 тестов парсера и обработка 20 документов локального checkout
Kubernetes без ошибок; предупреждения о неподдерживаемых шорткодах сохраняются.
Документация: [Mistune](https://mistune.lepture.com/en/latest/renderers.html),
[python-frontmatter](https://python-frontmatter.readthedocs.io/en/latest/).


Пустые и состоящие только из пробелов/переносов строк фрагменты исключаются
до нумерации частей и сборки соседних ID. Проверка использует `body.strip()`
только как условие: текст непустых фрагментов и отступы кода не обрезаются.
Если эмбеддер сообщил `Empty chunk text`, пересоберите чанки и передайте ему
путь новой версии, напечатанный чанкировщиком; старые версии не исправляются
на месте.
