# Лабораторная работа № 1 — Развёртывание и анализ LLM

## Описание задания

В рамках лабораторной работы был развёрнут локальный сервер Ollama и настроена отправка запросов к моделям через REST API, совместимый с OpenAI API. В эксперимент включены три модели: Qwen 2.5 3B, Llama 3.2 3B и Mistral 7B.

Для каждой модели использовались три задания:

- **P1 — генерация письма.** Модель должна написать письмо на заданную тему.
- **P2 — классификация обращений.** Модель должна отнести обращения к одному из трёх классов: `Billing`, `Tech support` или `Sales`.
- **P3 — извлечение данных.** Модель должна выделить восемь полей из описания ноутбука и вернуть их в формате JSON.

Каждое задание запускалось в двух режимах по два раза. В режиме **A** дополнительные параметры не задавались. В режиме **B** использовались настройки `temperature = 0.2`, `top_p = 0.85` и `max_tokens = 128`. Это позволило сравнить ответы и время выполнения в обоих режимах.

## Использованные технологии и модели

- **Ollama** — локальный запуск моделей.
- **REST API** — отправка запросов на `http://localhost:11434/v1/chat/completions`.
- **Python 3.14.0** — запуск эксперимента и обработка результатов.
- **requests** — отправка HTTP-запросов из Python.

В эксперименте использовались модели:

- `qwen2.5:3b` — Qwen 2.5, размер около 1,9 ГБ;
- `llama3.2:3b` — Llama 3.2, размер около 2,0 ГБ;
- `mistral:7b` — Mistral 7B, размер около 4,4 ГБ.

Все три модели были предварительно загружены и запускались по очереди.

## Параметры эксперимента

Сравнивались два режима:

- **A — базовый.** Параметры `temperature`, `top_p` и `max_tokens` не передавались. В этом случае Ollama использовала значения по умолчанию.
- **B — с настройками.** `temperature = 0.2`, `top_p = 0.85`, `max_tokens = 128`.

`temperature` влияет на случайность генерации: при меньшем значении ответы обычно менее разнообразны. `top_p` ограничивает набор токенов, из которых модель выбирает следующий. `max_tokens` задаёт максимальную длину ответа. Низкие значения `temperature` и `top_p` сами по себе не гарантируют правильный результат, а небольшой лимит токенов может привести к обрыву длинного текста.

Фиксированное значение `seed` не задавалось, поэтому два запуска одного задания могли дать разные ответы. Это позволило оценить стабильность выполнения одинаковых запросов.

## Результаты запуска

Основная серия запускалась командой:

```powershell
python source/experiment.py run --repeats 2
```

В результате получилось **36 основных прогонов**: 3 модели × 3 задания × 2 режима × 2 повтора. Все 36 запросов завершились без записанных технических ошибок — поле `error` во всех строках осталось пустым. При этом отсутствие технической ошибки не означает, что каждый ответ был правильным.

Скрипт сохранил ответы и метрики в файлы `answers.json`, `runs.csv`, `summary.csv` и `summary.md`. Дополнительно выполнены 18 коротких диагностических запросов для измерения скорости обработки промпта и генерации — по одному на каждое сочетание модели, задания и режима.

## Насколько совпадали повторные ответы

При сравнении повторов одного и того же задания полностью совпали **7 из 18 пар**, то есть **38,9%**.

- **Qwen:** совпали 3 пары из 6 — оба режима для P2 и режим B для P3.
- **Llama:** совпала 1 пара из 6 — режим B для P2.
- **Mistral:** совпали 3 пары из 6 — режим B для P2 и оба режима для P3.

Чаще всего отличались письма P1. При этом разные формулировки не всегда означают разные по смыслу ответы. С другой стороны, полное совпадение ещё не гарантирует, что ответ верный.

## Что изменилось после настройки параметров

**Qwen 2.5 3B.** Среднее время почти не изменилось: 6,19 с в режиме A и 6,11 с в режиме B. Автооценка осталась 1,000. По этим результатам нельзя сказать, что настройки заметно ускорили модель.

**Llama 3.2 3B.** Среднее время уменьшилось с 7,24 до 6,31 с, а автооценка выросла с 0,854 до 0,917. Но оба письма P1 в режиме B были незавершёнными: генерация дошла до 128 выходных токенов, а текст обрывался. В коде не сохранялось поле `finish_reason`, поэтому точную причину завершения запроса проверить по журналу нельзя. По длине и виду ответов можно предположить, что был достигнут лимит генерации.

**Mistral 7B.** Среднее время уменьшилось с 18,65 до 12,50 с, а автооценка выросла с 0,861 до 0,875. При этом средняя длина ответа уменьшилась примерно со 127 до 81 токена. Письма P1 в режиме B также обрывались на лимите в 128 токенов. Поэтому меньшее время не означает, что модель стала генерировать токены быстрее: ответы стали короче.

Сквозная скорость на токен в секунду изменилась так:

- Qwen: с 8,77 до 9,01;
- Llama: с 9,05 до 8,88;
- Mistral: с 5,47 до 5,39.

Значит, настройки повлияли на модели по-разному. Время ответа уменьшилось у Llama и Mistral, но в задании с письмом это сопровождалось обрывами текста. У Qwen время и оценки почти не изменились.

## Наблюдения по ответам

**P1 — письмо.** Qwen писал связно и по теме, но письма получились короче требуемых 80–120 слов. Автооценка не проверяет длину текста, поэтому поставила максимальный балл. У Llama встречались смешение языков и незаконченные фразы. В режиме B текст выглядел лучше, но тоже обрывался. Mistral отвечал медленнее, допускал грамматические ошибки и иногда добавлял сведения, которых не было в задании. В режиме B письма не всегда заканчивались.

**P2 — классификация.** Qwen и Llama правильно распределили все три обращения во всех запусках. Mistral один раз в базовом режиме ошибочно отнёс обращение об оплате к `Tech support`. В остальных запусках он дал правильные метки.

**P3 — извлечение данных.** Qwen вернул все восемь полей с правильными значениями. Mistral тоже вернул все поля и дословно повторил ответы в обоих запусках каждого режима. У Llama один базовый ответ содержал `screen_inches: null`, хотя диагональ была указана в описании. В других ответах некоторые числа были строками, а в названии модели появилось лишнее слово «Ноутбук».

## Ручная оценка ответов

Помимо автоматической оценки, сохранённые ответы были просмотрены, а файл `results/manual_review.csv` заполнен оценками по шкале от 1 до 5 и комментариями. Эта оценка субъективна и относится только к ответам из данного эксперимента.

| Модель | P1 — письмо | P2 — классификация | P3 — извлечение | Среднее |
|---|---:|---:|---:|---:|
| Qwen 2.5 3B | 3.50 | 5.00 | 5.00 | 4.50 |
| Llama 3.2 3B | 1.25 | 4.75 | 4.25 | 3.42 |
| Mistral 7B | 2.00 | 4.50 | 5.00 | 3.83 |

По ручной оценке Qwen лучше справился с заданиями в целом. При этом его письма всё равно были короче нужного объёма. Основные проблемы Llama связаны с письмами и отдельной ошибкой при извлечении поля. У Mistral хорошо получалось извлекать данные, но он медленнее отвечал и иногда ошибался в письмах или классификации.

### Ограничения автоматической оценки

Автоматические баллы нужно рассматривать как ориентир, потому что проверки в коде довольно простые.

- **P1:** проверяются отдельные признаки текста. Длина письма 80–120 слов и естественность русского языка не оцениваются. Поэтому балл 1,000 не означает, что письмо полностью соответствует заданию.
- **P2:** оценщик находит названия классов в тексте. Он может засчитать метки, даже если модель добавила нумерацию, хотя по условию нужно было вернуть только сами метки.
- **P3:** оценщик принимает числовые строки за числа и проверяет название модели по наличию ожидаемого текста. Поэтому некоторые ответы с неправильными типами или лишними словами могли получить слишком высокий балл. Полная проверка JSON-схемы не выполняется.

## Как запустить проект в Windows

### 1. Установить Ollama

1. Скачать установщик с сайта [ollama.com/download/windows](https://ollama.com/download/windows) и установить Ollama.
2. Запустить Ollama. По умолчанию сервер доступен по адресу `http://localhost:11434`.
3. Проверить установку в PowerShell:

```powershell
ollama --version
```

### 2. Скачать модели

Для загрузки моделей выполнить команды по очереди в PowerShell. Первоначальная загрузка требует подключения к интернету:

```powershell
ollama pull qwen2.5:3b
ollama pull llama3.2:3b
ollama pull mistral:7b
```

Список загруженных моделей проверяется командой:

```powershell
ollama list
```

### 3. Подготовить Python

Перейти в каталог `lab1_llm_analysis`. Например:

```powershell
cd C:\Users\<имя_пользователя>\Downloads\lab1_llm_analysis
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Если PowerShell не позволяет активировать окружение, выполнить команду для текущего окна, а затем повторить активацию:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
```

### 4. Проверить API

```powershell
python source/experiment.py check
```

Скрипт проверяет доступность Ollama, наличие моделей и возможность отправить тестовый запрос. Если какой-либо модели нет, выводится команда для её загрузки.

### 5. Запустить эксперимент

```powershell
python source/experiment.py run --repeats 2
```

Результаты постепенно записываются в `results/runs.csv`. После завершения доступны файлы `results/summary.md` и `results/summary.csv`. Ответы находятся в `answers.json`, подробные записи — в `runs.csv`. Файл `manual_review.csv` предназначен для ручной оценки ответов.

Другие варианты запуска:

```powershell
python source/experiment.py run --repeats 1
python source/experiment.py run --repeats 2 --skip-native-probe
python source/experiment.py run --repeats 2 --output-dir results_test
```

Если Ollama работает по другому адресу, задать его перед запуском:

```powershell
$env:OLLAMA_BASE_URL = "http://localhost:11434"
python source/experiment.py check
```
